# V1 MVP 目标

> V1 不是对真实转运业务的生产承诺，而是一个以真实访谈证据和明确 Assumption 为边界的作品集 MVP。真实仓库、支付、承运商和清关接入尚未获得确认。

## User Goal

用户应能在一个连续的入口中完成并理解一次中国 → 英国个人转运的核心任务：

```text
获得仓库信息
→ 预报并确认自己的 Package
→ 盘点并选择多个 Package
→ 创建并提交一次 Shipment
→ 查看仓库处理后的重量与报价
→ 完成支付确认
→ 自助查看离仓及后续履约状态
→ 在异常时知道下一步
```

V1 的目标不是替代所有人工支持，而是减少对**常规状态查询**的持续依赖；需要人工处理的异常应被清楚说明和引导。

## Product Goal

验证以下产品假设是否值得继续投入：

1. 以 Package 为单位呈现到仓归属和可操作状态，是否能帮助用户减少人工盘点与确认；
2. 将多个 Package 明确组织为一个 Shipment，是否能让用户理解并完成合箱提交；
3. 将重量、报价、支付、离仓和后续追踪分开表达，是否能让用户理解履约而不把付款误认为已发运；
4. 自助查看到仓确认、打包重量和离仓状态，是否能降低跨时区等待客服的需要。

这些是需要通过后续原型测试或更多真实使用反馈检验的 Product Assumption，不是预设的验证结果。

## Business Goal

若未来接入真实业务，V1 期望把以下重复、信息型人工沟通转为可自助获取的信息：

- “我的 Package 到仓并归属我了吗？”
- “这次将哪些 Package 合箱？”
- “称重和报价是多少？”
- “付款后是否已经离仓？”
- “Shipment 当前处于哪个履约阶段？”

这描述的是效率方向，而非虚构 KPI、节省工时或业务收益承诺。仓库核验、打包、异常裁决和末端承运商处理仍可能需要人工参与。

## MVP Success Condition

**当用户无需持续询问人工客服，即可确认自己的 Package、选择并提交一次 Shipment、查看最终重量与报价、完成模拟支付并区分已支付与已离仓、持续追踪至签收或获得异常下一步时，V1 的核心闭环即告成立。**

其中“模拟支付”“模拟外部状态”必须在作品集演示中明确标记；是否可替换为真实能力属于后续 Product Assumption。

## 非目标

- 不以提高下单量、GMV、留存或客服效率的具体数值作为 V1 成功标准；当前没有对应的真实基线数据。
- 不证明微信小程序一定优于网站或 App；当前只验证其是否能承载这条产品闭环。
- 不试图覆盖所有路线、仓库规则、异常类型或运营角色。
