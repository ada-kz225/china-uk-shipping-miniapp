# 产品定义

> 本阶段采用 **Assumption-led MVP Definition**。P01 的探索性访谈为部分设计提供直接证据，但不代表所有中英转运用户。未获得真实业务或多用户证据的内容继续标记为 **Product Assumption**。研究依据见 [../01-research/12-discovery-conclusion.md](../01-research/12-discovery-conclusion.md)。

## Product Positioning

**为在英国、一次需处理多个中国电商 Package 的留学生和华人个人用户，在国内包裹陆续到仓至英国签收的转运场景中，提供 Package 确认、合箱提交与 Shipment 履约可见性的自助入口，减少跨时区等待人工客服的状态查询。**

产品不以“功能丰富的物流平台”为定位；V1 聚焦一次转运是否能被用户清楚、连续地完成。

## Primary User

### V1 首要用户

**在英国、购买多个中国电商商品并进行周期性转运的中国留学生个人用户。**

这是一个有边界的 V1 选择，而不是对全部市场的断言。

| 判断维度 | 当前依据 |
| --- | --- |
| 真实任务证据 | P01 是英国留学生；最近一次转运约有 10–20 个来自多个中国电商渠道的 Package，并在积攒后合箱。 |
| 问题匹配度 | P01 需人工核对多个订单、确认到仓归属，并因没有网站/App而等待客服查询到仓、重量和离仓状态。 |
| 与 MVP 闭环匹配 | 该人群的真实旅程完整覆盖 Package 管理 → 合箱 → 报价/付款 → 离仓/追踪。 |
| 范围可控性 | 面向个人的单次 Shipment，避免一开始进入企业库存、批量发货和复杂运营能力。 |

“高频”在此指用户在一段时间内有多个中国电商 Package 需要汇集，不等同于所有用户都有高频转运。P01 约每 3 个月转运一次；频率、包裹量和适用范围仍需更广泛验证。

### Secondary Users

- **长期居住英国的华人个人用户：** 可能有相同的个人转运任务，但使用频率、地址复用和服务偏好仍是 Product Assumption。
- **有多店铺中国电商购买行为的英国个人用户：** 若也需要把多个 Package 合并为一次中国 → 英国 Shipment，可能共享核心闭环；是否属于首要用户仍待验证。

### V1 暂不重点服务的人群

- 单件、偶发且更适合直接寄送的个人用户；
- 代购、跨境卖家、企业客户或需要库存/财务管理的经营者；
- 需要多国家、多线路、多仓库调度的用户；
- 以仓库操作、承运商管理或客服工单为主要任务的运营人员。

这些人群不一定没有价值，但其任务会扩展 V1 的业务规则和能力边界。

## Core JTBD

### JTBD 1：确认和盘点 Package

> **When** 我在多个中国电商下单，国内物流已显示包裹送达仓库，  
> **I want to** 自助确认每个 Package 是否已到仓、是否归属自己，并盘点哪些仍在等待，  
> **So I can** 不必反复询问客服，也能判断本次是否可以开始合箱。

P01 直接支持“国内签收后仍确认到仓归属”与“人工盘点很麻烦”；是否适用于所有服务模式仍需验证。

### JTBD 2：将多个 Package 形成一次 Shipment

> **When** 我有一批已可处理的 Package，  
> **I want to** 选择本次要寄出的物品、表达必要的处理偏好并提交一次 Shipment，  
> **So I can** 清楚控制这次发什么、何时发，以及哪些物品留待下一次。

P01 的合箱、选取/排除 Package 和封箱前修改行为支持该任务；“自助选择是否比人工协调更重要”仍需验证。

### JTBD 3：确认付款后的履约进展

> **When** 我的 Shipment 已被称重、报价并完成付款，  
> **I want to** 自助查看打包重量、是否已离仓和后续阶段，  
> **So I can** 知道付款不等于已发运，并在异常时采取合适的下一步。

P01 直接指出重量、离仓是优先自助查询项；其并未认为报价难懂，也未直接说明支付成功确认方式。

## Product Problems

| Problem | Evidence | User Impact | Confidence |
| --- | --- | --- | --- |
| Package 到仓与个人归属无法自助确认，多个订单需要人工盘点 | P01 在国内物流签收后仍询问客服是否进入个人集合；人工核对订单被评价为“很麻烦”。 | 用户难判断哪些 Package 已可进入 Shipment，需要跨工具与人工沟通。 | Medium |
| 到仓确认、打包重量、离仓等关键仓库状态依赖客服回复 | P01 所用服务没有网站/App；时差下客服有时数小时后回复；三项均被点名为优先自助查询信息。 | 用户无法及时确认下一步或履约进展，付款后尤其要等待人工回复。 | Medium |
| 多个 Package 到一次 Shipment 的选择和仓库处理仍通过人工协调 | P01 会积攒、选取/排除 Package，选择服务，并在封箱前修改。 | 若不能清楚表达 Package 与 Shipment 的关系，用户无法可靠地提交一次明确的转运请求。 | Low |
| 英国末端状态停滞时，用户缺少可行动的信息 | P01 曾遇到 Royal Mail 长时间“派送中”且超过预计时间，后通过电话客服解决。 | 用户需要自行判断何时升级、联系谁；异常原因与频率未知。 | Low |

### 非 Top Problem，但必须承接的基础能力

P01 在付款前会查看称重、单价和人工打包费，但认为费用与计费重量清楚、通常符合预期。因此，**Quote / Payment 是完成闭环的基础能力，而不是当前证据支持的最高优先级痛点。** V1 应呈现可核对的重量与报价，不应凭空假设复杂的“价格教育”是主要价值。
