# V1 Out of Scope

> V1 的目标是验证一次个人转运闭环是否可以被清楚、自助地完成。以下能力被主动排除，不代表它们永远没有价值，而是因为其不解除当前核心任务阻塞，或需要未确认的真实外部能力。

## 因核心闭环价值低而暂不做

| 不做的能力 | 原因 | 未来进入条件 |
| --- | --- | --- |
| 优惠券、促销、裂变 | 不帮助用户确认 Package、形成 Shipment 或理解履约；当前没有需求证据。 | 核心闭环稳定后，有明确商业策略与用户价值证据。 |
| 积分、会员等级、成长体系 | 依赖复购、成本和权益规则；不属于首次转运的必要任务。 | 有重复使用与留存证据，且规则可解释。 |
| 推荐系统、内容社区、AI 导购 | 与当前“状态透明和转运决策”问题无直接关系。 | 出现明确任务和可评估价值后。 |
| 全量 Shipment 历史分析、费用比较 | 不阻塞首次闭环。 | 重复用户明确需要回顾/比较时。 |

## 因运营复杂度超出用户端 MVP 而暂不做

| 不做的能力 | 原因 | V1 的替代边界 |
| --- | --- | --- |
| 完整 WMS（入库、货位、拣货、装箱、库存） | 属于仓库运营系统，不是个人用户端的核心任务。 | 仅以用户可理解的 Package / Shipment 状态展示结果。 |
| 多仓库复杂调度、分仓路由 | 需要真实仓网、库存和履约规则。 | V1 假定一个 Warehouse 信息来源。 |
| 多国家、多线路、多币种、自动比价 | 会扩大计费、合规和承运商规则，且当前没有用户/业务证据。 | 只表达中国 → 英国的一条候选闭环。 |
| 企业账户、代购批量发货、财务对账 | 用户角色、审批与结算需求完全不同。 | 仅支持个人 User 的单次 Shipment。 |
| 完整客服系统、客服工单、SLA 管理 | 需要运营团队、知识库和服务规则。 | 仅提供最小 Exception 指引和支持入口方向。 |
| 复杂增值服务配置与实时价格 | 依赖仓库能力、服务限制、计费和责任规则。 | P1 仅保留有限服务偏好表达的可能性。 |
| 完整售后、退款、赔付和争议处理 | 需要责任、保险、证据与财务规则。 | V1 只说明 Exception 的影响和下一步。 |

## 因作品集阶段采用模拟而暂不做

| 不做的真实接入 | 原因 | MVP 表达方式 |
| --- | --- | --- |
| 真实 Warehouse 入库、称重、拍照和出库同步 | 当前无确认的仓库合作或数据接入。 | 使用明确标注的模拟状态/事件，不声称实时。 |
| 真实微信支付或其他支付渠道 | 无支付主体、合规配置和真实订单结算规则。 | 模拟 Payment 发起、成功和失败状态。 |
| 真实国际物流、清关、Royal Mail 等承运商 API | 无可靠的合作、权限、事件映射或数据质量确认。 | 使用阶段级模拟 Tracking Event，并标注数据模拟。 |
| 自动读取淘宝、拼多多等平台订单/物流 | 涉及平台授权、账户权限与数据合规，且并非 P01 直接提出的必须能力。 | 用户以最小预报信息建立 Package。 |
| 真实地址校验、禁运品/关税/清关申报判断 | 需要准确、合规且持续更新的外部规则。 | 仅将地址、清关和限制提示标为业务 Assumption。 |

## 明确的范围纪律

- 不因“转运产品看起来应该具备”而把上述能力移入 P0；
- 不以模拟状态冒充真实支付、仓库或承运商数据；
- 不把客服等待问题误解为“需要建设完整客服平台”；V1 优先解决常规状态的自助可见性；
- 不把 P01 使用的照片、加固、去包装和特快直接扩展成复杂增值服务商城。
