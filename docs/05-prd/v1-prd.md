- 未由研究直接确认的真实业务规则标记为 **Product Assumption**，不得伪装成已验证的服务政策。

## 2. Background & Problem

### Primary User

V1 聚焦于在英国、周期性从中国电商购买多件商品，并通过中国仓完成集运的中国留学生个人用户。P01 探索性访谈支持这是一个真实起始场景，但不代表广泛统计结论。

### Core JTBD

1. **当多个国内包裹陆续到达中国仓时，我想确认它们是否已到仓并归属自己，从而判断本次是否可以合箱。**
2. **当有一批可处理包裹时，我想选择本次要寄出的物品并提交一张转运单，从而控制这次发什么、何时发。**
3. **当转运单已称重、报价和付款后，我想自助确认是否离仓及后续履约，从而不把付款误认为已发运。**

### Top Product Problems

| Problem | 当前证据 | User Impact | Confidence |
| --- | --- | --- | --- |
| 到仓与个人归属无法自助确认 | P01 在国内物流签收后仍需询问客服是否已归入个人集合 | 用户无法判断包裹能否进入本次合箱 | Medium |
| 多个包裹需要人工跨工具盘点 | P01 一次约管理 10–20 个包裹，并认为人工核对订单麻烦 | 用户难以判断哪些包裹已齐、可合箱或需要等待 | Medium |
| 关键仓库状态依赖人工沟通 | P01 的到仓、重量、离仓查询依赖客服，受时差影响 | 用户无法即时确认履约下一步 | Medium |
| 英国末端状态停滞时缺少可行动的信息 | P01 曾遇到派送中停滞并自行联系承运商 | 用户不知道问题影响和应采取的下一步 | Low |

报价本身不是当前最高优先级痛点；但最终重量、报价、付款和离仓是完成交易与履约闭环所必需的基础能力。

## 3. Product Goals

### User Goal

用户无需持续询问人工客服，即可完成：

**确认包裹 → 选择合箱 → 提交转运单 → 查看最终报价 → 模拟付款 → 确认离仓 → 查看阶段级运输进度 → 签收或处理异常。**

### Product Goal

验证一条以包裹和转运单为核心实体、状态清晰且能处理 10–20 件包裹选择的 Assumption-led MVP 闭环是否成立。

### Business Goal

若接入真实业务，目标是将常规的到仓、重量、报价、离仓和运输状态查询转为自助可见，减少重复人工答复；本项目不设虚构 KPI 或实际效率结果。

### Success Condition

在 Happy Path 中，用户无需手工修改数据或绕过业务规则，即可从中国仓地址开始完成一次转运单的创建、报价、模拟付款、实际离仓状态确认与签收；在 Exception Path 中，用户能理解问题、影响、下一步和恢复结果。

### Non-goals

V1 明确不做：

- 会员、优惠券、积分、推荐或内容运营；
- 多国家线路、多仓调度、自动线路比价；
- 完整 WMS、完整客服 / 工单、企业账户；
- 复杂增值服务配置、赔付、退款；
- 真实微信支付、真实国内 / 国际物流 API、清关 API、英国末端 API；
- 自动读取淘宝、拼多多等平台订单或物流。

## 5. Persona / Primary Scenario

### Primary Persona

**在英国的中国留学生个人用户。** 其周期性购买多个中国电商商品，需要先寄送到中国仓，再选择其中一部分合箱寄往英国。

不虚构年龄、城市、收入或详细人口统计。该 Persona 基于一位真实 exploratory interview 的行为证据，是 V1 的设计起点，不是对所有用户的概括。

### Primary Scenario

用户一次管理约 10–20 个包裹：

1. 获取带个人识别信息的中国仓地址，在外部电商下单；
2. 用国内运单号与最小商品识别信息预报包裹；
3. 等待包裹分批到仓，盘点哪些已确认归属、哪些可合箱；
4. 从可合箱集合中选择其中一部分创建转运单；
5. 填写英国收货地址，提交后等待仓库处理、称重和最终报价；
6. 完成模拟付款，明确区分“已付款”和“已从仓库发出”；
7. 在同一转运单内查看国际运输、清关、英国派送、签收或异常下一步。

## 8. Functional Requirements

### FR-001 查看中国仓地址

#### User Story

作为准备在国内电商下单的用户，我想查看并复制我的中国仓收件信息，以便正确填写收货地址。

#### Description

首页展示中国仓地址入口；用户进入后可查看收件人、个人识别信息、电话和地址填写说明，并复制必要信息。

#### Preconditions

用户已进入小程序；可展示有效的仓库信息。具体地址格式为 Product Assumption。

#### Main Flow

1. 用户在首页点击“复制中国仓地址”；
2. 系统展示并复制必要的仓库收件信息；
3. 系统提示“下单后请返回预报包裹”；
4. 用户前往外部电商完成下单，小程序流程暂停。

#### Business Rules

- FR-001 不承担国内电商下单、订单读取或物流查询。
- 仓库地址不可用时，不展示过期或虚构地址。

#### UI / Interaction Requirements

- 用户可见标题：**中国仓地址**；主按钮：**复制地址**。
- 复制成功提示：**已复制。下单后请返回预报包裹。**

#### State Changes

无包裹或转运单状态变化。

#### Error / Exception Cases

仓库信息无法获取时，显示：**暂时无法获取中国仓地址，请稍后重试。**

#### Acceptance Criteria

- 用户可复制完整的中国仓收件信息；
- 页面明确说明外部下单不在小程序内完成；
- 用户不会因复制地址而创建包裹或转运单。

### FR-002 预报包裹与重复运单校验

#### User Story

作为已在国内下单的用户，我想提交国内运单号和最小商品识别信息，以便仓库后续匹配我的包裹。

#### Description

“预报包裹”使用最小表单创建一件包裹：国内运单号必填，订单截图或简短商品说明二选一必填；备注可选。

#### Preconditions

用户可访问自己的包裹列表；同一有效国内运单号尚未存在。

#### Main Flow

1. 用户在“包裹”页点击“预报包裹”；
2. 填写国内运单号，上传订单截图或填写商品说明；
3. 点击“提交预报”；
4. 系统校验信息和重复运单；
5. 成功后创建包裹，显示“已预报，等待送往仓库”。

#### Business Rules

- 包裹预报不代表已到仓。
- 同一有效国内运单号不得创建重复包裹。
- 是否所有实际包裹都必须预报是 Product Assumption；V1 按预报路径演示。

#### UI / Interaction Requirements

- 必填字段和按钮均使用中文：**国内运单号**、**商品识别信息**、**提交预报**。
- 成功提示：**预报成功，包裹到仓后将进入确认流程。**
- 重复提示：**该运单号已预报，无需重复提交。**

#### State Changes

创建 Package：**DECLARED**，用户显示：**已预报，等待送往仓库**。

#### Error / Exception Cases

- 缺少运单号：**请填写国内运单号。**
- 缺少商品信息：**请上传订单截图或填写商品说明，便于核对归属。**
- 提交失败：**暂未提交成功，请重试。** 保留表单输入。

#### Acceptance Criteria

- 系统只接受最小必填字段；
- 同一运单号重复提交不会生成第二件包裹；
- 成功、校验失败和技术失败都有中文反馈；
- 预报成功后不显示“已到仓”或“可合箱”。

### FR-003 包裹列表、详情与状态筛选

#### User Story

作为管理多件包裹的用户，我想在一处看到每件包裹是否到仓、是否归属自己、能否合箱或是否有问题，以便决定下一步。

#### Description

“包裹”页提供全部、待到仓、待确认、可合箱、已转运、需处理六类筛选；点击卡片进入“包裹详情”查看状态说明、预报信息、相关事件和关联转运单。

#### Preconditions

用户拥有至少零件包裹；列表仅返回用户本人拥有的包裹。

#### Main Flow

1. 用户进入“包裹”页；
2. 系统按用户可理解的状态分组展示包裹；
3. 用户切换筛选或点击某件包裹；
4. 系统展示状态、最近事件、可选性或关联转运单。

#### Business Rules

- 已到仓不等于已确认归属；已确认归属不等于已加入转运单。
- 只有 READY_FOR_SHIPMENT 对应的“可合箱”包裹可进入选择流程。
- 已加入转运单的包裹须显示关联转运单号，避免重复选择。

#### UI / Interaction Requirements

- 包裹卡至少展示：脱敏国内运单号、最小商品信息、中文状态、最近事件 / 更新时间、异常或关联转运单提示。
- 状态筛选使用中文：**全部、待到仓、待确认、可合箱、已转运、需处理**。
- 不在列表默认展示无决策价值的完整事件日志、最终费用或大量订单字段。

#### State Changes

列表和详情不主动改变状态；状态由 Warehouse / Ops 事件产生。

#### Error / Exception Cases

- 无包裹：**暂无包裹。下单后可预报国内运单号。**
- 筛选无结果：**该状态下暂无包裹。**
- 加载失败：**加载失败，请重试。**

#### Acceptance Criteria

- 用户可在不逐条进入详情的情况下盘点 10–20 件包裹的可用性；
- 每件不可选包裹有中文原因；
- 用户不可查看其他用户的包裹；
- 页面不直接显示英文内部状态码。

### FR-004 多包裹选择

#### User Story

作为准备合箱的用户，我想从可合箱包裹中多选本次要寄出的部分，以便创建一次清晰的转运单且不遗漏可选包裹。

#### Description

用户在“包裹”页点击“开始合箱”进入选择模式。系统允许选择一件或多件可合箱包裹，并持续提示已选择数量和未选择的可合箱数量。

#### Preconditions

至少存在一件用户本人拥有、无阻塞问题且状态为 READY_FOR_SHIPMENT 的包裹。

#### Main Flow

1. 用户进入“可合箱”筛选并点击“开始合箱”；
2. 勾选一个或多个可合箱包裹；
3. 系统固定显示“已选择 N 件”“可合箱但未选择 M 件”；
4. 用户点击“继续创建转运单”进入创建页。

#### Business Rules

- 只有 READY_FOR_SHIPMENT 可勾选。
- 待到仓、待确认、需处理和已加入有效转运单的包裹不可勾选，必须说明原因。
- 未选择的 READY_FOR_SHIPMENT 包裹仅提示，不阻止创建转运单。
- 草稿阶段不锁定包裹；提交成功后才锁定。

#### UI / Interaction Requirements

- 固定底栏主按钮：**继续创建转运单**。
- 不可选原因使用中文，例如：**正在确认归属，暂不可选**、**已加入转运单号 REF-••••**。
- 用户返回时保留当前勾选；主动放弃时提示：**放弃后，本次已选包裹将不再保留。**

#### State Changes

进入选择模式不改变 Package 状态。

#### Error / Exception Cases

若选择期间包裹变为不可选，系统标出该包裹并要求用户调整选择；不得静默移除。

#### Acceptance Criteria

- 用户可选择 8 件，同时清楚看见还有 2 件可合箱但未选择；
- 至少选择 1 件才能继续；
- 不可选包裹不能通过多选绕过规则；
- 选择模式不创建转运单或锁定包裹。

### FR-005 创建转运单与填写英国地址

#### User Story

作为已选择本次包裹的用户，我想确认所选包裹并填写英国收货地址，以便提交一张可履约的转运单。

#### Description

“创建转运单”页面展示已选包裹、可合箱但未选择的包裹提醒、一次性英国地址和提交前说明。该页不展示报价、支付或复杂服务商城。

#### Preconditions

用户从选择模式带入至少 1 件仍为 READY_FOR_SHIPMENT 的包裹。

#### Main Flow

1. 系统展示已选包裹数量及最小辨识信息；
2. 系统提示仍有 N 件可合箱但未选择的包裹；
3. 用户填写收件人、联系电话、邮编和详细地址；
4. 用户可返回编辑选择或移除已选包裹；
5. 用户进入提交转运单动作。

#### Business Rules

- 英国地址以本次转运单快照保存；地址簿属于 P1。
- 具体地址格式、校验逻辑和末端承运商限制均为 Product Assumption。
- 用户可提交部分可合箱包裹，不要求全部选择。

#### UI / Interaction Requirements

- 页面标题：**确认本次转运**。
- 区块标题：**已选包裹**、**还有 N 件可合箱包裹未选择**、**英国收货地址**。
- 地址字段使用中文：**收件人、联系电话、邮编、详细地址**。
- 用户可点击：**返回调整**、**移除**、**提交转运单**。

#### State Changes

仅创建 / 更新 Shipment Draft；包裹在本阶段尚未最终锁定。

#### Error / Exception Cases

- 地址缺失时逐字段提示，例如：**请填写收件人。**
- 已选包裹为 0 时禁用提交并提示：**请至少选择 1 件可合箱包裹。**

#### Acceptance Criteria

- 用户可查看、移除或返回调整已选包裹；
- 页面提示未选择的可合箱包裹但允许继续；
- 必填地址未完成时不能提交；
- 该页不新增服务偏好、地址簿或报价能力。

### FR-006 提交转运单、锁定包裹与生成转运单号

#### User Story

作为已确认包裹和地址的用户，我想提交转运单并获得可识别的转运单号，以便知道仓库将处理哪一次寄送。

#### Description

系统在提交时校验地址、包裹可用性和归属；成功后生成唯一且稳定的 Shipment Reference，用户界面显示为“转运单号”，并锁定已选包裹。

#### Preconditions

存在至少 1 件可选包裹，英国地址完整，且用户拥有当前草稿。

#### Main Flow

1. 用户点击“提交转运单”；
2. 系统校验包裹仍可选、未被其他有效转运单占用；
3. 系统创建转运单并生成转运单号；
4. 已选包裹进入已加入转运单状态；
5. 用户进入“转运单详情”，看到“已提交，等待仓库处理”。

#### Business Rules

- 一个 Package 同时只能属于一个有效 Shipment。
- 提交后 Package 锁定为 IN_SHIPMENT，Shipment 进入 SUBMITTED。
- 转运单号用于用户识别和关联事件，不等同于真实承运商单号。
- 重复提交必须幂等：返回已创建转运单，不再创建第二张。

#### UI / Interaction Requirements

- 提交中按钮显示：**正在提交**，并锁定重复点击。
- 成功提示：**转运单已提交，等待仓库处理。**
- 页面展示中文标签：**转运单号**，不得展示“Shipment Reference”。

#### State Changes

- Shipment：DRAFT → SUBMITTED；
- 已选 Package：READY_FOR_SHIPMENT → IN_SHIPMENT。

#### Error / Exception Cases

若某件包裹已不可选，显示：**部分包裹状态已变化，请返回调整后再提交。** 并指出具体包裹；保留其他草稿信息。

#### Acceptance Criteria

- 成功提交仅生成一张转运单和一个稳定转运单号；
- 已选包裹不能再被另一张有效转运单选择；
- 用户提交后可立即找到该转运单及其中文状态；
- 用户界面不展示 SUBMITTED、IN_SHIPMENT 等英文状态码。

### FR-007 转运单列表

#### User Story

作为有多次转运记录的用户，我想快速找到正在处理、待付款、在途或已完成的转运单，以便继续当前任务或查看历史。

#### Description

“转运”页按进行中和历史展示用户自己的转运单；列表卡展示转运单号、中文当前状态、是否需要处理、最近事件和包含包裹数。

#### Preconditions

用户已创建至少零张转运单。

#### Main Flow

1. 用户点击 TabBar 的“转运”；
2. 系统优先展示仍在进行中的转运单；
3. 用户点击卡片进入“转运单详情”；
4. 已签收或已取消记录可作为历史查看。

#### Business Rules

- 仅展示用户本人拥有的转运单。
- 进行中定义为未进入 DELIVERED 或 CANCELLED 的转运单。
- 状态排序优先级应优先于创建时间：需处理 / 待付款优先于普通在途。

#### UI / Interaction Requirements

- 页面标题：**转运**。
- 卡片字段使用：**转运单号、当前状态、最近更新、包含 N 件包裹、需要处理**。
- 空状态：**暂无转运单。选择可合箱包裹后可创建转运单。**

#### State Changes

无。

#### Error / Exception Cases

加载失败时显示：**加载失败，请重试。** 不显示为业务异常。

#### Acceptance Criteria

- 用户能在列表首屏优先找到需要付款或需要处理的进行中转运单；
- 用户能从历史记录进入详情；
- 列表不显示其他用户的转运单；
- 所有状态名称均为中文。

### FR-008 转运单详情、当前状态与下一步

#### User Story

作为已提交转运单的用户，我想打开详情就知道目前到哪一步、我是否需要操作和接下来会发生什么，以便不再反复询问状态。

#### Description

“转运单详情”是同一转运单的唯一事实中心。顶部始终展示转运单号、当前状态和下一步；内容区随状态动态展示仓库处理、最终报价 / 付款、运输进度、包含包裹、费用、英国地址和需要处理问题。

#### Preconditions

用户拥有该转运单。

#### Main Flow

1. 用户从首页、转运列表、创建成功或关联包裹进入详情；
2. 系统读取当前状态和最近事件；
3. 系统优先展示当前需要用户处理的区块；
4. 用户按状态执行付款、查看进度、查看包裹或遵循异常指引。

#### Business Rules

- 转运单号、当前状态、下一步始终在顶部。
- Quote、Payment、运输进度、异常均属于该转运单上下文，不拆为独立页面。
- Exception 出现时优先于普通 Timeline 展示。

#### UI / Interaction Requirements

- 顶部中文标签：**转运单号、当前状态、下一步**。
- 用户界面不显示英文的 Current Status、Next Action、Quote、Payment、Timeline 或内部状态码。
- 当前状态为“已付款，等待仓库发出”时，必须明确“当前无需操作，尚未实际离开仓库”。

#### State Changes

详情浏览本身不改变状态；付款等明确操作由对应 Requirement 驱动。

#### Error / Exception Cases

- 无权限或实体不存在时显示中文不可用提示，不暴露他人信息。
- 加载失败时提供“重试”，不将转运单改为“需要处理”。

#### Acceptance Criteria

- 任一用户可见状态均能回答：现在发生了什么、用户需不需要操作、下一步是什么；
- 用户在详情中可找到本次包含的包裹、地址及当前相关信息；
- 不额外新增报价、支付、物流或异常独立页面。

### FR-009 仓库处理与最终计费重量

#### User Story

作为已提交转运单的用户，我想知道仓库正在处理我的转运单，并在完成后看到最终计费重量，以便理解报价何时产生。

#### Description

Ops 通过模拟 Warehouse Event 将转运单推进为“仓库正在处理”，再记录打包完成和最终计费重量。用户端只展示处理事实与下一步，不要求用户参与仓库操作。

#### Preconditions

Shipment 已提交，包裹已锁定至该转运单。

#### Main Flow

1. 模拟 Ops 开始仓库处理；
2. 转运单详情显示“仓库正在处理”；
3. 模拟 Ops 完成打包和称重；
4. 系统记录最终计费重量，为生成最终报价提供前提。

#### Business Rules

- 仓库处理中不可由用户自由修改包裹或地址。
- 没有打包完成和最终重量，不得生成最终报价。
- 实际称重、体积重、计费重公式和处理时点均为 Product Assumption。

#### UI / Interaction Requirements

- 用户状态：**仓库正在处理**。
- 说明：**仓库正在检查、打包和称重，最终报价生成后会显示在这里。**
- 默认下一步：**当前无需操作。**

#### State Changes

Shipment：SUBMITTED → WAREHOUSE_PROCESSING；处理完成后由 FR-010 推进。

#### Error / Exception Cases

仓库处理发现阻塞问题时，进入 EXCEPTION；用户界面显示“需要处理”及具体影响，而不生成伪报价。

#### Acceptance Criteria

- 用户可以区分“已提交”和“仓库正在处理”；
- Quote 不能在最终重量记录前出现；
- 仓库操作在 Portfolio MVP 中可通过 mock、admin script 或 seeded event 触发。

### FR-010 生成最终报价快照

#### User Story

作为等待付款的用户，我想看到本次转运的最终计费重量、费用项和总价，以便在付款前核对。

#### Description

仓库处理完成后，系统为该转运单生成一个 Quote Snapshot，并将用户端状态变为“最终报价已生成，请确认并付款”。

#### Preconditions

仓库已完成打包；已记录最终计费重量；不存在阻塞性 Exception。

#### Main Flow

1. 模拟 Ops 生成最终报价；
2. 系统保存最终计费重量、费用项、总价、生成时间和版本 / 来源；
3. 转运单进入待付款状态；
4. 用户在详情中查看报价并进入模拟付款。

#### Business Rules

- Quote 至少包含：最终计费重量、费用项、运费、打包 / 必要处理费、总价、生成时间。
- 是否使用体积重、具体费用公式、币种、税费、报价有效期均为 Product Assumption。
- 付款成功后不得静默改写已接受的 Quote Snapshot。

#### UI / Interaction Requirements

- 中文区块标题：**最终报价**。
- 字段标签：**最终计费重量、运费、打包费、总价、报价生成时间**。
- 主按钮：**确认并模拟付款**。
- 不把任何模拟金额标记为真实报价或真实价目政策。

#### State Changes

Shipment：WAREHOUSE_PROCESSING → AWAITING_PAYMENT。

#### Error / Exception Cases

报价数据不完整或存在阻塞问题时，不能展示付款按钮；显示：**当前无法生成报价，请查看处理说明。**

#### Acceptance Criteria

- 用户能在付款前看到完整的 Quote Snapshot；
- Quote 与特定转运单唯一关联；
- 付款后 Quote 不被静默改写；
- 报价规则未验证部分在文档和演示中明确为模拟 / 假设。

### FR-011 模拟付款

#### User Story

作为已核对最终报价的用户，我想发起模拟付款并知道结果，以便让转运单满足后续出库条件。

#### Description

V1 提供明确标示的模拟付款。用户点击付款后，系统先进入“正在确认付款结果”；成功、失败和结果未知均有不同反馈。

#### Preconditions

Shipment 状态为 AWAITING_PAYMENT；存在有效 Quote Snapshot；不存在阻塞性 Exception。

#### Main Flow

1. 用户点击“确认并模拟付款”；
2. 系统锁定付款按钮，显示“正在确认付款结果”；
3. 模拟 Payment 返回成功；
4. 系统记录 Payment Result；
5. 页面显示“已付款，等待仓库发出”。

#### Business Rules

- Payment 成功是 Dispatch 的必要前提，但不等于 Dispatch。
- Payment 失败、取消或结果未知时不得出库。
- 真实支付渠道、支付确认机制和退款规则均为 Product Assumption，不进入 V1。

#### UI / Interaction Requirements

- 按钮：**确认并模拟付款**。
- 处理中：**正在确认付款结果，请勿重复操作。**
- 成功：**付款成功，等待仓库发出。**
- 失败：**付款未成功，请重新尝试。**

#### State Changes

- AWAITING_PAYMENT → PAYMENT_PROCESSING；
- 模拟成功：PAYMENT_PROCESSING → PAID_AWAITING_DISPATCH；
- 模拟失败 / 未完成：PAYMENT_PROCESSING → AWAITING_PAYMENT。

#### Error / Exception Cases

付款结果未知时，保持 / 回到待付款，展示：**暂未确认付款结果，请稍后刷新后再试。** 不得显示“已从仓库发出”。

#### Acceptance Criteria

- 付款 CTA 在处理期间不可重复触发；
- 成功后的中文状态为“已付款，等待仓库发出”；
- 失败后用户可重新付款；
- 成功付款不会自动把状态推进至已离仓。

### FR-012 实际出库状态

#### User Story

作为已付款的用户，我想确认转运单是否已实际离开仓库，以便知道履约是否真正开始。

#### Description

系统仅在模拟 Warehouse Dispatch Event 确认后，将转运单从“已付款，等待仓库发出”更新为“已从仓库发出”。

#### Preconditions

Payment 已成功；最终报价有效；打包和最终重量已确认；无阻塞性 Exception。

#### Main Flow

1. 用户付款成功后查看转运单详情；
2. 系统展示“已付款，等待仓库发出”，提示当前无需操作；
3. 模拟 Ops 通过出库校验并记录实际离仓事件；
4. 系统更新状态，Timeline 增加离仓事件；
5. 用户看到“已从仓库发出”。

#### Business Rules

- Dispatch 必须同时满足付款成功、打包 / 最终重量确认、有效 Quote、无阻塞问题和实际离仓记录。
- PAID_AWAITING_DISPATCH ≠ DISPATCHED ≠ DELIVERED。
- 出库时点、承诺时长和线路交接规则均为 Product Assumption。

#### UI / Interaction Requirements

- 付款后未出库：**已付款，等待仓库发出**；说明：**付款已成功，当前无需操作。仓库确认实际出库后会更新运输进度。**
- 已出库：**已从仓库发出**。
- 不得使用“已发货”替代实际离仓事实。

#### State Changes

Shipment：PAID_AWAITING_DISPATCH → DISPATCHED。

#### Error / Exception Cases

若已付款但出库受阻，进入 EXCEPTION，明确显示：**付款已成功，但当前无法安排出库。** 并说明下一步。

#### Acceptance Criteria

- 用户能清楚区分付款成功与实际出库；
- Dispatch 前 Timeline 不出现国际运输节点；
- 仅 Ops / 模拟事件可推进至 DISPATCHED。

### FR-013 阶段级运输进度与签收

#### User Story

作为已出库的用户，我想在一条连续时间线上看到国际运输、清关、英国派送和签收，以便知道转运单当前处于哪个阶段。

#### Description

转运单详情在实际离仓后展示“运输进度”。模拟 Tracking Event 按时间顺序映射为阶段级中文事件，而非承诺实时承运商轨迹。

#### Preconditions

Shipment 已处于 DISPATCHED 或后续履约状态。

#### Main Flow

1. 模拟 Dispatch Event 写入离仓节点；
2. 模拟 International Tracking、Customs、UK Last Mile 和 Delivery Event 按顺序进入；
3. 系统更新当前中文状态和运输进度；
4. 用户查看最近事件及下一预期阶段。

#### Business Rules

- Timeline 至少覆盖：已从仓库发出 → 国际运输中 → 清关中 → 英国派送中 → 已签收。
- 每个事件至少记录阶段、时间、用户可理解说明和来源标识（如有）。
- 无新事件时显示“尚无新进展”，不编造航班、时效或承运商信息。
- 只有收到签收事实时才能进入 DELIVERED。

#### UI / Interaction Requirements

- 区块标题：**运输进度**。
- 用户状态依次为：**已从仓库发出、国际运输中、清关中、英国派送中、已签收**。
- 页面按时间顺序展示；当前节点突出显示。

#### State Changes

DISPATCHED → INTERNATIONAL_TRANSIT → CUSTOMS_CLEARANCE → UK_LAST_MILE → DELIVERED。

#### Error / Exception Cases

运输、清关或末端事件出现业务问题时，进入 EXCEPTION；Technical Error 仅显示：**加载运输进度失败，请重试。**

#### Acceptance Criteria

- 用户可在同一转运单详情查看连续运输阶段；
- Timeline 不在出库前显示为已运输；
- “已签收”只能在模拟签收事件后出现；
- 所有 Timeline 标题与事件说明均为中文。

### FR-014 业务异常与恢复

#### User Story

作为遇到包裹或转运单问题的用户，我想知道发生什么、影响什么、我需要做什么和问题进展，以便采取正确行动或等待处理。

#### Description

Package 或 Shipment 的业务异常以实体详情中的条件区块显示。用户不能自行把异常标记为已解决；只有模拟 Ops Resolve Event 可恢复主流程。

#### Preconditions

发生可识别的业务问题，例如归属无法确认、处理阻塞、付款失败或运输异常。

#### Main Flow

1. 模拟 Ops / 外部事件创建异常；
2. 关联实体进入 EXCEPTION；
3. 页面展示发生什么、影响、用户下一步、当前进展和支持；
4. 用户仅在明确要求时补充信息或执行操作；
5. 模拟 Ops 解决问题，系统恢复至恰当主流程状态。

#### Business Rules

- Exception 必须关联具体 Package 或 Shipment。
- 阻塞性 Exception 阻止相关阶段继续，例如未匹配包裹不得合箱、出库受阻不得进入 DISPATCHED。
- Exception 不是自动取消，也不是用户可自行完成的状态。
- 真实异常类型、责任边界、时效、赔付和退款政策均为 Product Assumption。

#### UI / Interaction Requirements

Exception 区块必须按中文显示：

1. **发生什么**
2. **影响什么**
3. **你需要做什么**
4. **当前进展**
5. **需要帮助**

若无需用户操作，必须明确写：**当前无需操作，正在处理。**

#### State Changes

任一 Package / Shipment 主状态 → EXCEPTION；解决后恢复至相应 Package 或 Shipment 主状态。

#### Error / Exception Cases

Technical Error 不得创建业务异常。用户补充信息提交失败时，保留 Exception 并显示：**提交失败，请重试。**

#### Acceptance Criteria

- 用户能看到异常关联的具体包裹或转运单；
- 用户知道是否需要操作，且可执行动作明确；
- 用户不能直接点击“已解决”；
- 恢复后页面说明已回到哪个中文状态。

### FR-015 首页任务路由

#### User Story

作为打开小程序的用户，我想先看到当前最需要处理的事情，以便不用在多个模块中寻找入口。

#### Description

首页严格按以下信息优先级组织：**待处理事项 → 当前转运 → 包裹概览 → 中国仓地址**，不是功能九宫格。

#### Preconditions

用户进入小程序。

#### Main Flow

1. 系统检查用户当前的异常、待付款、需补充信息、可合箱包裹和进行中转运单；
2. 首页优先呈现一个最高优先级行动；
3. 用户点击卡片进入关联包裹详情、转运单详情或包裹筛选；
4. 若无包裹，首页提供中国仓地址与预报引导。

#### Business Rules

- 行动优先级：需用户处理的阻塞性问题 > 待付款 > 需补充信息 > 可合箱包裹。
- 已签收和已取消转运单不占据默认首页 Current Journey。
- 首页只聚合任务，不替代包裹列表或转运单详情的事实来源。

#### UI / Interaction Requirements

- 区块中文标题：**待处理事项、当前转运、包裹概览、中国仓地址**。
- 待付款 CTA：**查看报价并付款**。
- 可合箱 CTA：**查看可合箱包裹**。
- 无包裹引导：**复制中国仓地址**。

#### State Changes

无；首页仅路由至实体任务。

#### Error / Exception Cases

局部模块加载失败时显示中文重试提示，不阻塞其他已加载模块。

#### Acceptance Criteria

- 首页不出现功能九宫格；
- 用户可从首页进入当前最高优先级待办；
- 无 Package 用户能在首屏找到复制中国仓地址的入口。

### FR-016 空、加载、技术错误与状态刷新

#### User Story

作为用户，我想在暂无数据、加载中、失败或状态变化后获得准确且可理解的反馈，以便不会将技术问题误认为业务问题。

#### Description

核心页面为 Empty、Loading、Technical Error 与 Business Exception 提供不同表现；用户重新进入页面、下拉刷新或小程序回到前台时可读取当前状态和最近事件。

#### Preconditions

用户进入首页、包裹列表、转运列表、详情或表单页面。

#### Main Flow

1. 页面初次加载时展示骨架或加载反馈；
2. 成功后展示当前实体状态；
3. 用户刷新或回到前台时重新读取状态；
4. 无数据时显示场景化空状态；
5. 技术失败时显示重试；业务问题时显示异常信息结构。

#### Business Rules

- Technical Error ≠ Business Exception。
- 模拟事件只能由预设操作 / 流程产生；刷新不能凭空推进状态。
- 无新事件时必须显示最后更新时间或“尚无新进展”。

#### UI / Interaction Requirements

| 场景 | 中文用户文案 / 行为 |
| --- | --- |
| 无包裹 | **暂无包裹。下单后可预报国内运单号。** |
| 无转运单 | **暂无转运单。选择可合箱包裹后可创建转运单。** |
| 加载中 | 显示骨架或 **正在加载**，不以空状态替代。 |
| 加载失败 | **加载失败，请重试。** |
| 无新事件 | **尚无新进展。** |
| 提交中 | **正在提交，请勿重复操作。** |

#### State Changes

无；刷新仅读取已有状态。

#### Error / Exception Cases

网络或读取失败时保留已成功加载的事实（如有），提供“重试”；不得将页面变为“需要处理”。

#### Acceptance Criteria

- Empty、Loading、Technical Error 与 Business Exception 具有不同中文表现；
- 刷新不会越过状态机；
- 所有按钮、Toast、Modal 和校验消息不得直接显示英文内部代码。

## 9. State Definitions

### 9.1 Package States

| Internal Code | User-facing Copy | Entry Condition | Available Action | Exit Condition |
| --- | --- | --- | --- | --- |
| DECLARED | 已预报，等待送往仓库 | 用户提交最小预报信息 | 暂无需操作 | 国内物流 / 模拟事件开始送往中国仓，或进入需要处理 |
| INBOUND_TO_WAREHOUSE | 正在送往仓库 | 国内包裹已发出或模拟在途事件 | 暂无需操作 | 中国仓物理收货，或进入需要处理 |
| ARRIVED_PENDING_MATCH | 已到仓，正在确认归属 | 中国仓记录物理收货，尚未完成匹配 | 当前无需操作；仅在明确要求时补充信息 | 确认归属后可合箱，或进入需要处理 |
| READY_FOR_SHIPMENT | 可合箱 | 已归属用户且无阻塞问题 | 选择加入本次转运单，或继续等待 | 提交转运单后已加入本次转运，或进入需要处理 |
| IN_SHIPMENT | 已加入本次转运 | 转运单提交成功并锁定该包裹 | 查看关联转运单 | 合规取消时回到可合箱，或进入需要处理 |
| EXCEPTION | 需要处理 | 出现归属、信息或处理阻塞问题 | 按明确指引操作，或等待处理 | 问题解决后恢复至适当主状态 |

### 9.2 Shipment States

| Internal Code | User-facing Copy | Entry Condition | Available Action | Exit Condition |
| --- | --- | --- | --- | --- |
| DRAFT | 正在准备本次转运 | 用户已选择包裹，尚未提交 | 调整包裹、填写地址、提交或放弃 | 提交、或取消草稿 |
| SUBMITTED | 已提交，等待仓库处理 | 用户确认包裹和英国地址后提交 | 查看包含的包裹；当前通常无需操作 | 仓库开始处理、处理前取消或需要处理 |
| WAREHOUSE_PROCESSING | 仓库正在处理 | 模拟 Ops 开始检查、打包、称重 | 当前无需操作；按明确提示处理 | 生成最终报价或进入需要处理 |
| AWAITING_PAYMENT | 最终报价已生成，请确认并付款 | 最终重量和 Quote Snapshot 已生成 | 核对报价、确认并模拟付款 | 进入付款结果确认或合规取消 |
| PAYMENT_PROCESSING | 正在确认付款结果 | 用户发起模拟付款 | 等待结果，不重复付款 | 付款成功或回到待付款 |
| PAID_AWAITING_DISPATCH | 已付款，等待仓库发出 | 模拟付款成功 | 当前无需操作；查看最近事件 | 仓库实际出库或出库问题 |
| DISPATCHED | 已从仓库发出 | 模拟 Ops 记录实际离仓 | 查看运输进度 | 国际运输或运输问题 |
| INTERNATIONAL_TRANSIT | 国际运输中 | 模拟国际段事件进入 | 当前无需操作 | 清关中或运输问题 |
| CUSTOMS_CLEARANCE | 清关中 | 模拟清关阶段事件进入 | 默认无需操作；仅按明确提示处理 | 英国派送中或清关问题 |
| UK_LAST_MILE | 英国派送中 | 模拟英国末端事件进入 | 当前无需操作；按异常指引处理 | 已签收或末端问题 |
| DELIVERED | 已签收 | 模拟签收事件进入 | 查看历史记录 | 正常履约结束 |
| EXCEPTION | 需要处理 | 任一阶段出现阻塞性业务问题 | 执行明确动作或等待处理 | 问题解决后恢复恰当阶段 |
| CANCELLED | 已取消 | 在实际离仓前按规则取消 | 查看相关包裹，需要时重新创建转运单 | 符合规则的包裹恢复可合箱 |

**PAID_AWAITING_DISPATCH ≠ DISPATCHED ≠ DELIVERED。**
对应的用户文案必须分别为：**已付款，等待仓库发出**、**已从仓库发出**、**已签收**。

## 10. Business Rules

本节复用并冻结既有 BR-001 至 BR-028，不新增业务规则。重点约束如下：

| Rule Group | 已冻结规则 |
| --- | --- |
| Package ownership | 用户只能查看、选择和提交自己拥有的包裹和转运单。 |
| Duplicate declaration | 同一有效国内运单引用不得重复创建包裹；重复请求必须可识别。 |
| Package eligibility | 只有已归属且无阻塞问题的 READY_FOR_SHIPMENT 包裹可加入转运单。 |
| One active Shipment | 一个 Package 任一时刻只能属于一个有效 Shipment。 |
| Lock / release | 草稿不锁定；提交后锁定；仅在允许取消 / 撤回时恢复为可合箱。 |
| Shipment Reference | 提交时生成稳定且唯一的转运单号；它不是承运商单号。 |
| Quote Snapshot | 报价记录最终重量、费用项、总价、生成时间和来源 / 版本；付款后不得静默改写。 |
| Payment / Dispatch Gate | 已付款、打包 / 最终重量确认、有效报价、无阻塞问题和实际离仓记录共同构成出库条件。 |
| Exception Blocking | 阻塞性问题阻止对应状态继续，例如未匹配包裹不可合箱。 |
| Exception Recovery | 仅 Ops Resolve Event 可使实体离开 EXCEPTION 并恢复恰当阶段。 |
| Status Event Record | 收货、匹配、打包、重量、报价、付款、出库、运输和异常的关键变化记录来源、时间、前后值和原因（如适用）。 |

具体取消窗口、价格、税费、支付、仓库操作、承运商、清关及末端规则继续为 Product Assumption。

## 15. Acceptance Criteria

### Scenario A：Happy Path

**Given** 用户已进入小程序，且模拟事件环境可用。

1. 用户在首页查看并复制中国仓地址；
2. 用户返回后预报 12 件包裹；
3. 模拟事件使其中 10 件成为“可合箱”，其余 2 件显示“待到仓”或“待确认”；
4. 用户进入选择模式，选择其中 8 件；
5. 系统显示“已选择 8 件”“还有 2 件可合箱包裹未选择”，但允许继续；
6. 用户创建转运单，填写英国地址并提交；
7. 系统生成唯一转运单号，锁定 8 件包裹；
8. 模拟 Ops 开始处理、完成打包称重并生成最终报价；
9. 用户查看最终计费重量、费用项和总价，完成模拟付款；
10. 用户看到“已付款，等待仓库发出”，且不被误导为已发运；
11. 模拟 Ops 记录实际出库，用户看到“已从仓库发出”；
12. 模拟事件依次推进为“国际运输中 → 清关中 → 英国派送中 → 已签收”；
13. 用户全程不需要修改数据库、不需要手工绕过锁定 / 状态规则，也不需要依赖未定义的客服操作。

### Scenario B：Exception Path

**Given** 已存在包裹或转运单。

1. 模拟 Ops / 外部事件在某一阶段创建业务异常；
2. 关联包裹或转运单显示“需要处理”；
3. 用户能查看发生什么、影响什么、你需要做什么、当前进展和需要帮助；
4. 若需要用户资料，用户按明确指引提交；若无需操作，用户看到“当前无需操作，正在处理”；
5. 用户不能自行标记异常已解决；
6. 模拟 Ops Resolve Event 解决问题；
