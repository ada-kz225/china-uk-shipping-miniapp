# Discovery 阶段正式结论

> 本结论基于前期问题研究与一位独立真实受访者 P01 的探索性访谈。P01 不是代表性样本；本文不将单个用户经历表述为大众需求或市场结论。P01 原始记录见 [P01.md](user-research/interviews/P01.md)，假设校准见 [hypothesis-validation.md](hypothesis-validation.md)。

## Evidence-backed

以下陈述有 P01 的直接访谈证据支持，但仅描述 P01 的经历：

1. P01 是英国留学生，约每 3 个月进行一次中国 → 英国转运；其最近一次包含约 10–20 个来自多个中国电商渠道的 Package。
2. P01 会主动预报订单截图和运单号，并在国内物流显示签收后继续确认仓库是否实际收到、是否归入个人集合。
3. P01 会人工核对多个电商订单是否齐全，并明确表示这种核对“很麻烦”。
4. P01 会主动决定何时合箱、纳入或排除哪些 Package，并在封箱前选择/修改运输方式、加固和去包装等处理。
5. P01 在封箱称重和确认报价后付款；其认为费用和计费重量清楚易懂，且价格通常符合预期。
6. P01 付款后只能通过微信客服确认是否离仓；服务方没有网站/App，受中英时差影响，人工回复有时需等待数小时。P01 点名希望自助查询到仓确认、离仓状态与打包重量。
7. P01 会使用国际物流网站、客服和英国末端承运商追踪；曾遇到英国派送状态停滞，最终通过 Royal Mail 电话客服解决。

## Directionally Supported

以下方向得到 P01 支持，但只有一个独立样本，仍要求更广泛验证：

1. **多 Package 汇集并创建一次 Shipment 是一个真实用户任务。** P01 的 10–20 件 Package 会被积攒、盘点、选择后合箱。
2. **Package 到仓归属与完整性可见，是用户完成合箱决策的基础。** P01 不把国内物流签收视为足够信息，仍需确认仓库实际收货与个人归属。
3. **Package 与 Shipment 应被视为不同实体和不同阶段。** P01 先管理多个 Package，再选择一次 Shipment；称重、付款和离仓发生在后续阶段。
4. **仓库关键状态的自助可见性是明确的产品机会。** P01 的到仓确认、重量和离仓查询都依赖人工客服，并受到时差影响。
5. **付款与实际离仓应分开呈现。** P01 已付款后仍关注包裹是否离仓；但其如何确认支付成功尚未获得直接证据。
6. **异常信息需要至少指向下一步支持。** P01 的英国派送异常需要其主动电话联系承运商；异常类型与频率仍未知。

## Assumptions

以下仍是 Product Assumption，不能被 P01 单样本或前期逻辑推演替代：

- 英国中国留学生、长期居英华人和高频中国电商购买者中，哪一类是最有价值的首要用户；
- 多 Package 的频率、规模、合箱偏好与主要痛点是否在更广泛用户中成立；
- 是否每一个 Package 都必须预报，以及预报、归属和仓库验收的真实业务规则；
- 运费公式、计费重量、人工打包费、增值服务、付款方式和“3 天离仓”等具体业务规则；
- 微信小程序是否比网站/App更适合作为主要入口；当前仅有“需要自助数字化入口”的单样本证据；
- 仓库、支付、国际运输、清关与英国末端事件是否可以真实接入、如何更新、是否可信；
- 地址复用、通知、照片凭据、异常自助处理在 MVP 中的优先级与适用范围。

## Product Problems to Solve

| Problem | Evidence | Impact | Confidence |
| --- | --- | --- | --- |
| Package 到仓与个人归属无法自助确认，多个订单还需要人工盘点 | P01 在国内物流签收后仍询问客服是否已入个人集合；手工核对订单被其评价为“很麻烦”。 | 用户难以判断哪些 Package 已可进入本次 Shipment，且需要跨工具和人工沟通。 | Medium |
| 到仓确认、打包重量、离仓等关键仓库状态依赖客服回复 | P01 所用服务没有网站/App；中英时差下客服有时数小时后才回复；上述三项是其点名的自助优先查询事项。 | 用户无法在需要时即时确认下一步或履约进展，付款后尤其需要等待人工回复。 | Medium |
| 多个 Package 到一次 Shipment 的选择与仓库处理仍通过人工协调 | P01 会积攒、选取/排除 Package，选择服务并在封箱前修改。 | 这是核心任务链的一部分；若不能清晰表达 Package 与 Shipment 的关系，用户无法自助完成一次可确认的转运请求。 | Low |
| 英国末端出现状态停滞时，用户缺少可行动的异常信息 | P01 曾遇到 Royal Mail 长时间“派送中”且超过预计时间，最终自行电话联系解决。 | 用户需要自行判断何时升级、联系谁；但异常原因、频率与适合的产品介入深度未知。 | Low |

### 明确不作为当前 Top Problem 的事项

**“报价不透明”不应进入当前 Top Problems。** P01 会查看重量、单价和人工打包费再支付，但认为费用与计费重量清楚、通常符合预期。报价仍是核心交易节点，产品应保留清楚可核对的表达；只是没有证据把它定义为首要痛点。

## Product Direction

当前产品方向是面向个人用户的**转运过程自助信息与决策入口**：先帮助用户确认自己的 Package、盘点并形成 Shipment，再让其在重量、报价、付款与离仓之间获得连续且可查询的事实，最后提供最小的履约追踪与异常指引。

```text
确认 Package 到仓/归属
→ 盘点并选择 Package
→ 创建一次 Shipment
→ 查看仓库处理后的重量与报价
→ 支付后确认离仓
→ 追踪至签收；异常时知道下一步
```

该方向优先解决信息可得性与决策连续性，不以复制仓库运营、构建复杂客服系统或扩展营销能力为起点。

## 是否可以进入 MVP Definition

**可以进入 Assumption-led MVP Definition。**

理由：核心用户场景、JTBD 和最小任务链已经清楚；多 Package → Shipment、到仓确认、合箱、重量报价及支付后离仓均获得了 P01 的部分或直接行为证据。对个人作品集而言，这已经足以定义一个边界明确、可被后续测试的 MVP，而不是声称已经完成市场验证。

### 可作为当前 MVP 设计依据

- P01 所代表的“英国留学生 + 多中国电商 Package + 周期性转运”是一个有真实行为证据的起始场景；
- Package 到仓/归属、Package 盘点、Package → Shipment 选择、重量/报价、支付后离仓应组成连续的核心任务链；
- 自助查询应优先覆盖到仓确认、打包重量与离仓状态；
- Package 与 Shipment、付款与离仓、正常追踪与异常处理应在概念上区分。

### 必须保留为 Assumption 的内容

- MVP 是否以微信小程序而不是网站/App 承载；
- 真实预报、报价、支付、出库、运输和异常规则；
- 外部状态数据与交易能力的可用性；若没有接入，作品集演示必须明确标记为模拟；
- 目标人群范围、包裹规模和功能优先级在其他真实用户中的适用性。

进入 MVP Definition 后，应把这些 Assumption 显式写入范围、状态设计和演示边界，并使用后续原型测试或更多访谈校准，而不是隐藏不确定性。
