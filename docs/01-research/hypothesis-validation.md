# P01 访谈后的假设校准

> 本文只基于一位独立真实受访者 P01 的近期中国 → 英国转运经历，以及其结构化访谈记录。它是 **exploratory interview** 的收敛，不代表市场样本、用户比例或普遍需求。`Supported` 表示“有 P01 的直接访谈证据支持”，不表示“已验证大众需求”。原始访谈记录为私有研究材料，不纳入公开仓库；逐样本记录见 [06-hypothesis-validation-table.md](user-research/06-hypothesis-validation-table.md)。

## 判定方式

| 结论 | 本文中的含义 |
| --- | --- |
| Supported | P01 的真实行为或明确描述与假设直接一致。仍需要更广泛验证。 |
| Partially Supported | P01 支持假设的一部分，但另一部分没有直接证据或存在重要边界。 |
| Not Supported | P01 的具体经历与假设相反。单个反例不代表假设已被普遍推翻。 |
| Insufficient Evidence | P01 没有提供足以判断该假设的直接行为或偏好证据。 |

## 核心假设结论

| ID | Product Assumption | P01 结论 | 具体访谈证据 | 解释与边界 |
| --- | --- | --- | --- | --- |
| A01 | 用户存在多 Package 集运需求 | **Supported** | P01 最近一次转运约有 10–20 个 Package，来自淘宝、拼多多、小红书；其会等待并积攒一批商品后再寄送。 | 该任务在 P01 的一次真实经历中明确存在。不能据此推断其他留学生或个人用户的包裹规模、频率或普遍性。 |
| A04 | 合箱是核心操作 | **Supported** | P01 会决定何时开始合箱、哪些 Package 本次不装；可在封箱前修改选择，并会按易碎、体积占用和紧急程度选择加固、去包装或特快。 | 合箱是 P01 从多个 Package 形成一次 Shipment 的真实决策环节。P01 没有明确说“选择 Package 本身很困难”，因此不能把“合箱存在”直接等同于“合箱界面复杂是普遍痛点”。 |
| A05 | 用户关心计费重量和报价 | **Supported** | P01 在封箱称重后查看重量和报价，再通过微信转账付款；会将结果与已知单价比较，且知道不超过 20 元的人工打包费。 | 计费重量与报价是 P01 的实际付款决策输入。反例/边界是：P01 认为费用与计费重量清楚易懂、通常符合预期；“价格不透明”不能作为当前的证据型核心问题。 |
| A06 | 用户需要区分支付成功和实际出库 | **Partially Supported** | P01 描述付款至离仓通常有“3 天内”的服务承诺；付款后只能通过客服查询是否离仓，并把离仓查询列为优先自助任务。 | P01 明确需要把付款后的“是否已离仓”作为独立信息获取。其未说明如何确认支付成功，因此“支付成功确认”这一半仍需验证。 |
| A09 | 微信小程序适合作为主要用户入口 | **Insufficient Evidence** | P01 因服务方没有网站或 App 而依赖微信客服，且受时差影响有时需等待数小时；其认为网站或 App 会更方便，并希望自助查询到仓、离仓和打包重量。 | 这支持“需要数字化自助入口”，但 P01 没有比较微信小程序、网站与原生 App，也没有表达对小程序的偏好。因此不能将入口选择写成已获支持。 |

## 对 MVP 决策的影响

### 可作为当前设计依据

- **Package 与 Shipment 应分开表达。** P01 的多个 Package 会在其主动决定后形成一次转运/打包请求。
- **Package 到仓归属需要可见。** 国内物流显示送达后，P01 仍需要确认仓库已收到且已归入个人集合。
- **合箱前的 Package 选择与封箱前修改应被视为关键任务。** 这是 P01 实际执行的决策，而不是凭空设想的操作。
- **重量、报价、付款与离仓是不同节点。** 即使 P01 对费用没有困惑，付款后仍有独立的离仓确认需要。
- **自助查看应优先覆盖到仓确认、打包重量和离仓状态。** 这是 P01 主动指出的优先顺序。

### 仍须保留为 Product Assumption

- 多 Package 合箱的任务强度、频率和适用人群范围；
- 是否每一个 Package 都必须预报，以及预报的真实业务规则；
- 支付成功如何确认、3 天离仓承诺是否稳定，以及真实支付/出库事件能否接入；
- 运费公式、收费范围、服务可选项和时效规则；
- 微信小程序是否优于网站或 App，及其是否适合作为主要入口；
- 运输、清关、英国派送状态的数据来源、更新质量和异常责任边界。

## 未得到支持的错误推断

- 不应把 P01 对价格清晰的评价改写为“用户普遍不关心费用”，或反过来写为“价格普遍不透明”。
- 不应把 P01 使用微信客服改写为“用户偏好微信小程序”。当前证据只说明人工沟通存在等待成本。
- 不应把一次 Royal Mail 派送延迟改写为“国际物流始终不透明”。P01 认为新旧物流单号的切换是清楚的。
- 不应把 P01 的约 10–20 件、约每 3 个月一次的经历作为所有目标用户的典型规模。
