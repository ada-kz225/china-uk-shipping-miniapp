# 用户需求收敛：从观察到需求方向

> 本文将 P01 的观察转译为 MVP 定义可使用的需求方向。它不设计页面、信息架构或技术方案，也不将单个样本的体验外推为普遍事实。每项方向都应在后续 MVP 测试和更多研究中继续校准。

| Observed Problem | User Need | Product Requirement Direction | 证据边界 |
| --- | --- | --- | --- |
| 国内物流显示签收后，P01 仍无法自行确认仓库是否实际收到并归入个人集合 | 用户需要知道每个预期 Package 是否已被仓库接收、是否已匹配到自己 | 系统需要以 Package 为单位呈现预期/到仓确认/归属等可理解事实，并显示最近更新时间或依据 | 直接观察于 P01；预报是否所有服务都必需、仓库事件如何获得仍是 Product Assumption。 |
| P01 要人工查看多个电商订单和客服照片，判断 Package 是否齐全，过程“很麻烦” | 用户需要在决定 Shipment 前盘点本次可处理的 Package，减少跨工具核对 | 系统需要集中呈现用户的 Package 集合及其当前状态，支持用户判断哪些已到仓、哪些仍在等待 | P01 未实际发生漏件/错件；跨用户的频率和影响仍需验证。 |
| P01 会选择/排除本次 Package、选择运输方式与附加处理，并在封箱前修改 | 用户需要把多个可用 Package 明确组成一次 Shipment，并知道何时还能修改 | 系统需要保持多个 Package 与一个 Shipment 的关系，表达选择、服务偏好和提交/封箱前的可修改边界 | 观察到真实行为；P01 未将选择过程描述为主要痛点。 |
| P01 在封箱称重、核对单价和人工打包费后才付款 | 用户需要在付款前获得可核对的最终重量、总价及费用构成 | 系统需要把仓库处理后的计费重量、报价与费用项关联到对应 Shipment，并清楚区分预估与最终结果（若真实业务存在预估） | P01 认为费用清楚；真实计费规则、预估价是否存在仍为 Product Assumption。 |
| 付款后 P01 只能通过客服查询是否离仓，且将离仓列为优先自助查询项 | 用户需要独立确认支付后的履约推进，尤其是是否已离仓 | 系统需要把支付、离仓和后续运输呈现为独立且连续的 Shipment 事实，并提供自助查询 | P01 没有说明支付成功如何被确认；真实支付和出库事件来源待确认。 |
| 服务方没有网站/App，P01 的到仓、离仓和重量信息依赖微信客服；时差下有时等待数小时 | 用户需要在需要时自行查看高频、高价值信息，而不是等待人工回复 | 系统需要优先提供到仓确认、打包重量和离仓状态的自助可见能力；入口形态待后续决定 | 直接支持数字化自助方向，不直接支持微信小程序优于网站/App。 |
| P01 在英国末端曾遇到状态长期“派送中”、超过预计时间，最终电话联系 Royal Mail | 用户需要在物流异常时知道当前影响、可采取的下一步及适合的联系对象 | 系统需要为 Shipment 关联可理解的最新运输事件；发生异常时应提供明确的状态说明和下一步支持指引 | 单一异常案例；原因、时长、责任边界和是否可自助解决仍未知。 |
| P01 依赖验货、物品总览和分层装箱照片确认商品状态与打包过程 | 用户需要可核对的仓库处理凭据，以建立对 Package 状态和装箱结果的信心 | 若真实仓库能稳定提供，系统可将 Package/Shipment 凭据与相关状态关联展示 | 仅 P01 证据；照片是否属于所有用户的核心需求、产生成本和业务规则待确认。 |

## 当前的最小需求链

```text
确认 Package 已到仓并归属自己
→ 盘点可处理的 Package
→ 选择多个 Package 形成一次 Shipment
→ 查看仓库处理后的重量与报价
→ 支付后确认是否离仓
→ 追踪至签收；异常时知道下一步
```

这条链是当前进入 MVP Definition 的**设计依据**，不是已验证的真实业务流程。外部仓库、支付和物流数据尚不能假定可用；作品集中的相应状态应在后续明确其模拟边界。
