# 访谈综合分析框架

> 本文件定义分析方法，不填写任何访谈结果。访谈完成后，应从匿名化的原始记录出发逐步归纳；不能从预设功能、单句偏好或研究者个人经历直接跳到产品需求。

## 分析路径

```text
Raw Interview
→ Observation
→ Pain Point
→ Need
→ Pattern
→ Product Insight
```

### 各层定义

| 层级 | 定义 | 应写什么 | 不应写什么 |
| --- | --- | --- | --- |
| Raw Interview | 原始、匿名化的访谈记录 | 用户按时间讲述的行为、工具、情境、简短原话 | 研究者对原因的推断或功能方案 |
| Observation | 可由原始记录直接支持的行为观察 | “P02 在三个工具之间对照单号后才确认包裹是否齐全” | “所有用户需要统一包裹页” |
| Pain Point | 特定情境下妨碍用户完成任务的困难 | “无法确认哪些包裹已到仓，导致延迟决定是否提交” | “缺少一个按钮” |
| Need | 用户在该情境下想达成的结果 | “在提交前确认每件包裹的可操作状态” | 具体页面、组件、技术方案 |
| Pattern | 两个或更多独立样本中反复出现的相似行为/困难，或一个高影响反例 | 说明相同点、不同点、样本范围和反例 | 以小样本宣称普遍市场规律 |
| Product Insight | 基于 Pattern 的、可影响后续产品取舍的判断 | “状态表达需要区分到仓与可提交，并保留来源/时间” | 直接指定视觉、页面结构或功能细节 |

## Feature Idea 的正确位置

**Feature Idea** 是为满足已识别 Need 的候选解法，不等于 Need 本身。

```text
用户说：“我每次要翻聊天记录和快递页，才知道还有没有包裹没到。”
    ↓
Observation：用户跨工具核对多个包裹状态
    ↓
Pain Point：信息分散，难确认是否齐件
    ↓
Need：在做寄送决定前确认每件包裹的状态
    ↓
Pattern：需至少与其他独立样本比较，或记录反例
    ↓
Product Insight：若模式成立，应优先支持 Package 状态可见性
    ↓
Feature Idea：包裹清单、状态标记、到仓通知……（仅候选解法）
```

不能把“用户说想要一个按钮”直接写成产品需求。应追问：该按钮要帮助完成什么任务？目前如何解决？频率和影响是什么？是否有其他更小的解法？

## 单次访谈分析步骤

1. 完成一份匿名化 `Interview P0x` 原始记录，不在记录中提前写结论。
2. 标记真实的行动、等待、工具切换、人工沟通和异常时刻。
3. 为每个时刻写 Observation，并链接到原始行为或简短原话。
4. 仅在任务被阻断、反复确认、增加成本或造成显著不确定时，形成 Pain Point。
5. 将 Pain Point 转写为用户想达成的 Need；暂不提出功能。
6. 对照 A01–A12，写入 Supports、Contradicts、Mixed 或 No evidence 的证据方向。
7. 明确记录反例、样本限制、记忆不确定和未追问项。

## 跨访谈综合步骤

1. 将独立样本的 Observation 放入主题簇；研究者本人 Self Journey 单独标注，不与独立样本等权计数。
2. 比较相同主题下的情境、频率、严重度、替代方案和反例。
3. 只有在证据足够具体且有跨样本一致性时，提出 Pattern；否则保留 `Insufficient Evidence`。
4. 从 Pattern 形成 Product Insight，并回填至假设验证表。
5. 需求优先级必须基于任务阻断程度、重复性、替代方案不足和实现/业务可行性，不根据受访者人数简单投票。

## Affinity Mapping

建议先按下列主题将 Observation 归类。它们是起始标签，不是固定分类；真实访谈可以新增、合并或删除主题。

| 初始主题 | 可归类的观察 |
| --- | --- |
| Package visibility | 单号记录、到仓确认、可操作状态、遗漏/重复确认 |
| Consolidation | 等待包裹、选包裹、合箱/不合箱决策、提交边界 |
| Pricing | 重量理解、报价时点、费用透明度、价格预期差 |
| Payment | 付款方式、支付确认、支付失败、付款后预期 |
| Warehouse | 收货、验货、称重、打包、出库等用户可见信息 |
| Tracking | 国际运输、清关、英国末端、签收、查询触发 |
| Exception | 包裹、地址、费用、支付、运输问题及处理 |
| Communication | 客服触发、沟通工具、回复、人工依赖 |
| Trust | 信息来源、时间、凭据、价格/状态可信度 |

## 证据强度与结论纪律

| 情况 | 可采用的表述 |
| --- | --- |
| 一个独立样本的具体经历 | “P0x 的经历显示……”；不能泛化 |
| 多个独立样本有相似行为，但情境不同 | “在本轮样本中出现了一个待进一步验证的模式……” |
| 证据相互矛盾或样本不足 | “Insufficient Evidence” 或 “Partially Supported”，并说明限制 |
| Self Journey 与独立样本一致 | “研究者经历与若干独立样本方向一致，但不增加独立样本数量” |
| 未发生的流程或无具体回忆 | “No evidence in this interview”，不等于“不存在” |
