# 半结构化用户访谈提纲

## 研究目的

了解近期有中国 → 英国寄送或集运经验的个人用户，如何在真实情境中完成购买、入仓、合箱、报价、支付、追踪和异常处理。重点是还原实际行为、工具和决策，而不是验证访谈者预设的功能。

本提纲不产生研究结论；只有在真实访谈完成并被规范记录后，才能更新假设状态。

## 目标对象与筛选

### 建议招募条件

- 近期有一次从中国寄送物品到英国的实际经历，或使用过面向该路线的集运服务；“近期”窗口由研究计划明确。
- 以个人收件/寄送需求为主，不把企业批量物流与个人旅程混合。
- 愿意按时间顺序回顾一次真实经历；可自行决定是否展示订单、物流或支付记录。

### 不应收集的内容

- 身份证件、银行卡、完整住址、完整运单、聊天记录等不必要敏感信息。
- 未经明确同意的录音、截图或屏幕录制。

## 访谈开场（约 3 分钟）

可以这样说明：

> 我在研究个人用户从中国寄东西到英国的真实过程，不是在推销某个服务，也没有标准答案。希望你回忆最近一次经历，按实际发生的顺序描述。你可以跳过任何问题，也不需要展示私密信息。我们关注的是流程和困难，不评价你的选择。

确认是否同意记录笔记；如需录音，单独获得同意。

## 访谈主线：最近一次真实经历（约 30–40 分钟）

### 1. 背景与触发

- 上一次从中国寄东西到英国是什么时候？
- 当时为什么需要寄？寄的是什么类型的物品？
- 当时是自己购买、亲友寄送，还是其他情况？
- 在开始前，你考虑过哪些替代方式？最后为什么选择现在的做法？

可追问：这次是单件还是多件？这类事情对你来说多久发生一次？不要要求受访者给出精确频率，先理解实际情境。

### 2. 从购买到仓库地址

- 从购买商品开始，到最终收到货，可以按照时间顺序讲一下整个过程吗？
- 当时如何知道商品应该寄到哪里？仓库地址从哪里获得？
- 填写国内收件地址时，你做了哪些操作？有没有不确定的字段？
- 有没有发生过地址、姓名、电话或识别信息填写问题？当时如何处理？

观察点：信息来源、跨平台切换、记录方式、是否依赖他人/客服。

### 3. 国内包裹与预报

- 下单后，你如何知道每个国内包裹的运单号？
- 你当时需要把单号或商品信息提供给集运服务方吗？如果需要，是怎么做的？
- 如果没有提供，服务方如何知道包裹属于你？
- 这一步中，哪些信息最难找、最容易漏或最不想重复填写？

可追问：当时有多少个包裹？来自几个商家/快递？如何记录或核对？

### 4. 到仓与包裹确认

- 你如何判断包裹已经到集货仓，而不只是国内快递显示签收？
- 收到过哪些通知、消息或状态？哪些内容对你有帮助，哪些让你困惑？
- 当你等多个包裹时，如何判断哪些已经齐了、哪些还在路上？
- 有没有出现过包裹无法找到、信息对不上、到仓很久没更新等情况？

### 5. 合箱与提交寄送

- 当时你如何决定什么时候发、是否等待其他包裹？
- 最后哪些包裹一起寄？为什么这样组合？
- 合箱/提交寄送时，你需要提供哪些信息？哪些信息重复填写或容易出错？
- 提交后，你是否能修改包裹或收件信息？如果需要改，当时怎么做？

避免问法：“合箱是不是核心功能？”应先让用户描述是否发生、为何发生和替代方式。

### 6. 称重、报价与付款

- 你是什么时候知道费用的？当时看到哪些价格或重量信息？
- 你如何判断这个价格是否能接受？有没有不理解或想确认的地方？
- 当时通过什么方式付款？付款前后分别发生了什么？
- 付款后，你怎么知道包裹是否已经可以/已经出库？
- 有没有遇到付款失败、补款、改价、退款或费用争议？

### 7. 国际运输、清关与英国配送

- 包裹从中国仓离开后，你如何查询它的进展？
- 你实际看过哪些状态、网站、消息或单号？哪个最有用？
- 哪一次你最想知道包裹在哪里？当时发生了什么？
- 清关或英国本地派送阶段，你是否收到过信息、需要做过什么？
- 你如何确认最终已经签收？

### 8. 异常与人工支持

- 最近一次过程中，最麻烦的事情是什么？请具体讲讲当时发生了什么。
- 你是否联系过客服、商家、仓库或承运方？为什么在那个时刻联系？
- 联系后你需要提供什么信息？多久得到什么结果？
- 如果没有联系过人工，是什么让你不需要联系？
- 你希望在问题发生时先看到什么信息，才知道下一步怎么做？

### 9. 使用工具与替代方案

- 整个过程中，你实际使用过哪些工具：电商平台、微信聊天、网站、表格、物流查询页、App 或其他？
- 每个工具各自帮你完成什么？在哪一步要在它们之间切换？
- 有没有你自己建立的记录方式，例如备忘录、Excel、聊天收藏或截图？为什么这么做？

### 10. 收尾

- 回头看这次经历，如果只能改进一个环节，你会先改哪一个？为什么？
- 有没有我没有问到、但对这次寄送很重要的事情？
- 之后如需澄清访谈笔记，是否愿意接受一次简短回访？

## 中立提问守则

- 问“发生了什么”“你当时怎么做”“为什么这样做”，不问“你会不会喜欢某功能”。
- 对每个积极评价追问具体行为和反例；对每个困难追问频率、影响、现有解决方法。
- 不承诺未来一定提供某项服务，不为用户解释或辩护现有流程。
- 当受访者没有经历某一步时，如实记录“未发生”，不强行追问以填满旅程。

## 访谈记录如何转化为产品输入

每条候选结论必须从具体事实开始，不能直接从意见跳到功能：

| 访谈记录中的行为/证据 | Pain Point | Need | Product Requirement（待验证） |
| --- | --- | --- | --- |
| 用户在多个工具间对照国内单号与仓库消息，仍无法确认是否齐件 | 信息分散，难以判断包裹是否齐全 | 在同一位置确认每件 Package 的状态和不可操作原因 | 提供按用户归属的 Package 清单与到仓/可合箱状态；需继续验证普遍性 |
| 用户称重后不知道报价为何变化，只能询问人工 | 价格产生过程不透明 | 在支付前理解应付金额和计费依据 | 报价应呈现总额、计费基础、生成时间和下一步；真实规则待确认 |
| 用户付款后反复查询是否离仓 | 支付与出库关系不清 | 知道付款是否成功及后续履约何时开始 | 将支付结果与出库事件分开呈现；需验证是否为高频问题 |

### 归纳步骤

1. 记录原始时间线、行为、使用工具和原话；
2. 标出任务被阻断、反复确认或依赖人工的时刻；
3. 将具体困难抽象为 Pain Point，并保留反例；
4. 写出用户想达成的 Need，而不是先写页面或按钮；
5. 形成可验证的 Product Requirement；
6. 将对应结论回填到 [08-validation-plan.md](08-validation-plan.md)，更新状态时附上证据和限制。
