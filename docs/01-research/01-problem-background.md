# 问题背景：中英个人集运

> 本文描述待验证的产品问题空间，不是对实际线路、服务规则、用户行为或市场规模的事实声明。凡是未通过真实研究或业务资料确认的判断，均应视为 **Product Assumption**。

## 什么是中英个人集运场景

中英个人集运可以理解为：用户从中国的电商平台、商家或亲友处获得一个或多个包裹，先寄往中国集货仓，再由服务方把这些包裹集中处理并寄送至英国收件地址。

这不是一个单一物流动作，而是一条由多段交付和多方协作组成的过程。用户通常需要在国内购物、仓库收货、包裹合并、费用确认、跨境运输与英国收件之间不断获取信息、作出选择并处理例外情况。实际服务流程会因线路、商品、服务商和英国末端交付方式而不同，具体规则待确认。

## 用户为什么可能需要集运

以下是合理但尚待验证的需求动机：

- 用户想购买只能或更适合从中国获取的商品，但收件地址在英国。
- 用户的一次购物来自多个店铺或商家，形成多个国内包裹；他们可能希望集中处理，而不是分别安排国际寄送。
- 用户希望在价格、等待时间、包裹数量、服务限制和安全感之间做取舍。
- 用户需要一个能持续确认包裹和订单状态的服务入口，而不希望完全依赖人工问询。

这些动机不代表所有用户都会选择集运。是否存在稳定需求、哪些动机最强、用户现在如何解决，都需要通过访谈、任务观察或业务资料验证。

## 为什么国内购买不等于英国收货

中国电商订单完成后，商品通常只完成了国内商家到国内地址的履约。若用户的最终收件地址在英国，仍可能面临以下额外任务：

1. 获取并正确填写中国集货仓收件信息；
2. 在获得国内快递单号后，确认包裹能被仓库识别并归属到自己；
3. 判断哪些包裹已经到仓、哪些适合一起处理；
4. 提供英国收件信息，并选择可用的转运服务；
5. 等待仓库验收、合箱、称重和报价；
6. 确认费用并完成付款；
7. 在跨境、清关和英国末端派送期间确认进度；
8. 在地址、费用、包裹或运输出现问题时配合处理。

这是一条候选用户旅程，不应被表述为所有服务商或所有用户的标准流程。

## 集运服务可能承担的角色

从用户视角，集运服务的潜在价值不只是“替用户寄一票国际快递”，还包括：

| 服务角色 | 用户需要解决的事情 | 应验证的问题 |
| --- | --- | --- |
| 集货入口 | 提供中国仓收件信息，使多个国内包裹能在同一处汇集 | 用户是否因仓库地址、识别码或填写方式而出错？ |
| 包裹归属与可见性 | 将国内运单、仓库实物和用户账户匹配 | 用户是否看不清包裹是否已经可处理？ |
| 合并决策支持 | 帮助用户决定哪些包裹放入同一次转运 | 用户是否真的需要/重视合箱，决策依据是什么？ |
| 价格确认节点 | 在仓库处理后呈现费用并让用户确认 | 最终费用如何产生、何时确认、用户是否理解？ |
| 履约信息入口 | 将复杂的跨境交付过程翻译成用户可理解的状态和下一步 | 用户最需要哪些事件、是否已有足够替代工具？ |
| 异常协同入口 | 在问题发生时说明影响、所需行动和处理进度 | 哪些异常最常见，用户何时必须依赖人工？ |

## 主要参与方（候选服务蓝图）

| 参与方 | 可能承担的角色 | 用户关心的交接信息 |
| --- | --- | --- |
| 用户 | 下单、预报包裹、选择合并方式、确认费用、收件/处理问题 | 包裹是否属于自己、下一步、费用、预计进展 |
| 中国电商商家/亲友 | 发出商品或提供物品 | 商品是否发出、国内运单号 |
| 国内快递服务 | 将包裹送至中国集货仓 | 国内运单状态、是否已签收至仓库 |
| 中国集货仓 | 收货、匹配、验收、合箱、称重、出库 | 到仓确认、异常、计费基础、是否已出库 |
| 跨境运输/清关相关服务 | 完成国际干线与清关环节 | 是否在运输、是否有清关问题、是否需要补充信息 |
| 英国末端派送服务 | 将 Shipment 送至英国收件地址并反馈签收 | 派送进度、签收事实、失败派送或地址问题 |

实际参与方、责任边界、数据来源和服务承诺尚未确认；该表只用于识别信息在交接处可能断裂的位置。

## 用户需要完成的关键任务

以用户任务而非页面为中心，候选任务包括：

```text
理解服务和仓库地址
→ 在中国渠道完成购物
→ 记录/预报国内包裹
→ 确认到仓与可处理状态
→ 选择多个包裹并提交一次转运
→ 确认称重后的费用并支付
→ 跟踪国际履约直至英国签收
→ 必要时处理异常
```

产品发现阶段的目标是验证：这些任务是否真实存在、哪些最痛、用户目前采用什么替代方案，以及微信小程序是否能在其中提供更低成本的解决方式。
