# Discovery 阶段总结

> 当前 Discovery 包含问题分析、假设池与一位独立真实用户 P01 的探索性访谈。P01 提供了方向性行为证据，不代表广泛用户样本。完整收敛见 [12-discovery-conclusion.md](12-discovery-conclusion.md)。

## 1. 当前有证据的核心问题

以下问题直接观察于 P01，仍需扩大验证：

1. **Package 到仓与归属难以自助确认。** 国内物流显示签收后，P01 仍需要确认仓库是否真正收货、是否进入个人集合。
2. **多个订单需要人工盘点。** P01 需跨电商订单和客服照片检查是否齐全，并明确表示很麻烦。
3. **关键仓库状态依赖人工客服。** P01 的到仓确认、打包重量和离仓查询没有自助入口；中英时差下回复有时等待数小时。
4. **英国末端异常缺少清晰的下一步。** P01 曾因派送状态停滞而改为电话联系承运商。

P01 未将“报价不透明”描述为问题：其认为重量、单价与人工打包费清楚，且通常符合预期。因此，费用表达是核心交易信息，但不是当前证据支持的首要痛点。

## 2. 核心用户与任务

目前唯一有直接访谈证据的起始用户是：**一位约每 3 个月转运一次、从多个中国电商购买生活用品等物品的英国留学生。**

长期居英华人和其他高频中国电商购买者仍是候选用户，而非已确认的目标人群。

由 P01 行为支持的暂定 JTBD 是：

> 当我有多个来自中国电商的 Package 要寄往英国时，我想确认哪些已到仓且归属自己、选择本次一起寄出的物品，并在付款后自行知道是否离仓和后续进度，从而不必反复等待客服回复。

这不是通用用户宣言，仍需通过更多样本验证。

## 3. 产品机会

当前产品机会是建立一个以 Package 与 Shipment 为中心的自助信息和决策入口：

```text
确认 Package 到仓/归属
→ 盘点与选择 Package
→ 创建一次 Shipment
→ 获得重量与报价
→ 支付后确认离仓
→ 追踪至签收；异常时获得下一步指引
```

P01 点名最希望自助查询的三项是：**到仓确认、离仓状态、打包重量**。

## 4. 当前关键假设

以下内容仍为 Product Assumption：

1. 多 Package 合箱是否在更广泛用户中高频且高价值；
2. 是否所有 Package 都必须预报，以及真实仓库归属规则；
3. 付款成功确认、出库承诺和报价规则的真实业务实现；
4. 微信小程序是否比网站/App更适合作为主要入口；
5. 仓库、支付和物流状态是否可真实接入并可靠展示；
6. 异常、照片凭据、地址复用和通知是否应进入首版。

## 5. 为什么可以进入 MVP Definition

本项目可以进入 **Assumption-led MVP Definition**：P01 已支持一条真实的多 Package → Shipment 旅程，并暴露出到仓归属、人工盘点、付款后离仓和自助状态查询的具体问题。

这不等于市场验证完成。MVP 必须把真实规则和外部数据能力标注为 Assumption 或模拟边界，并避免把未证实的功能扩展写成用户刚需。
