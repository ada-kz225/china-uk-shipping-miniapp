# 需求假设：从用户问题到可能能力

> 本文件不等于功能清单或 PRD。它记录一条可质疑、可验证的链条：只有当用户问题成立、用户需要明确且产品假设被支持时，候选能力才应进入后续产品定义。所有“产品需求假设”均为 **Product Assumption**。

## 核心需求假设

| 用户问题 | 用户需求 | 产品需求假设 | 可能的产品能力 | 需要验证什么 |
| --- | --- | --- | --- | --- |
| 不知道多个国内包裹是否都已到仓 | 希望统一查看自己预期/已收到的包裹及状态 | 如果以 Package 为单位集中记录预报、到仓和可操作状态，用户能更容易判断包裹是否齐全 | 包裹预报；Package 列表；到仓状态；到仓通知 | 用户是否真的需要手工预报；哪些状态/字段足够判断“齐全” |
| 国内快递显示签收后，仍不知道仓库能否处理 | 希望知道当前是否需要自己操作，以及下一步是什么 | 如果区分“预报、到仓验收、可合箱、需处理”，并提供行动提示，可减少状态理解成本 | 状态解释；事件时间；下一步提示；异常原因 | 用户能否理解这些状态；仓库能否可靠提供事件 |
| 多个 Package 难以决定本次一起发哪些 | 希望从可用包裹中选择一次要寄出的组合，并避免重复或遗漏 | 如果系统只展示可合箱 Package，并把选中的多个件锁定到一个 Shipment，用户能更有把握地提交转运 | 可合箱包裹池；多选；Shipment 草稿/提交；不可选原因 | 多包裹是否高频；用户按什么标准选择；是否需要等待/拆分 |
| 提交合箱后，不知道仓库正在做什么、何时有价格 | 希望知道仓库处理进度和等待原因 | 如果 Shipment 以“已提交—仓库处理中—待支付”表达用户决策状态，可降低不确定性 | Shipment 状态；仓库处理进度；报价就绪通知 | 用户真正关心的等待信息和可接受等待时长 |
| 最终运费不确定，不知道何时、为何要支付 | 希望在支付前看懂收费依据、金额和付款后果 | 如果仓库实测后产生可解释报价，并以明确支付状态作为出库闸门，用户能作出知情决策 | 报价明细；计费重量说明；待支付；支付结果；待出库状态 | 真实价格规则、币种、税费、报价变更/有效期与用户关注度 |
| 支付成功后仍不知道包裹是否离仓 | 希望看到付款、出库和后续履约的因果关系 | 如果支付和出库被表示为独立、连续的 Shipment 事件，用户不会把付款或打包误解为已发运 | 已支付；待出库；已出库；状态通知 | 实际支付确认和仓库出库数据来源；用户是否需要主动提醒 |
| 国际运输、清关、英国派送状态难懂或分散 | 希望在一个位置确认当前阶段、最后更新和是否需要行动 | 如果将可信物流事件归纳为用户语言的阶段时间线，可降低查询与客服依赖 | Shipment 时间线；最近事件；来源/时间；末端追踪信息（如可用） | 用户需要的事件粒度；承运商数据可用性；是否已有充分替代方案 |
| 地址、支付、包裹或运输异常时只能反复人工沟通 | 希望知道问题影响、自己该做什么、处理到哪一步 | 如果异常被关联到具体 Package/Shipment，显示行动和进度，可减少信息不对称 | 异常提示；需用户操作；处理状态；支持入口 | 异常类型/频率/责任；用户是否需要自助操作或只需清晰沟通 |
| 重复用户反复填写英国收件信息 | 希望复用常用地址，同时不影响已提交订单 | 如果将地址作为可复用资产并在 Shipment 中保存快照，可减少重复填写和错误 | 地址簿；默认地址；地址快照 | 重复寄送比例、地址变化率、英国地址校验需求 |

## 需求依赖关系

```text
Package 可见性
    ↓
可合箱选择
    ↓
Shipment 提交
    ↓
仓库处理与报价
    ↓
支付确认
    ↓
出库与履约时间线
    ↓
签收/异常处理
```

这条链路意味着：

- 没有可靠的 Package 归属与状态，就不能让用户可信地选择合箱；
- 没有报价与支付规则，就不能把“提交合箱”变成交易闭环；
- 没有履约事件，就不能把“已出库”描述为成功签收；
- 没有异常规则，任何理想路径的闭环都缺少真实世界的兜底。

## 后续优先验证的假设

1. 用户是否有“统一管理多 Package 并合箱”的真实、高影响任务？
2. 状态透明和下一步提示，是否能减少用户的查询/客服依赖？
3. 称重后报价与付款，是否是用户完成转运的关键决策点？
4. 用户需要什么粒度的运输状态，现有替代方案在哪里不足？
5. 地址复用和异常自助信息，是否足以进入首版而非后续优化？

若研究不支持某一假设，应移除或替换对应能力，而不是因为它“看起来像物流产品应有功能”而保留。
