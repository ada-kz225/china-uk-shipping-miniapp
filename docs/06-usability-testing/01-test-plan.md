# Exploratory Usability Testing Plan

> 本轮测试验证已完成的低保真可点击原型是否支持核心任务完成，不是需求访谈、市场调研或功能优先级讨论。本文不包含任何测试结果。

## 1. Research Objective

验证用户是否能在没有主持人导航或界面解释的情况下，理解并完成以下已冻结的 V1 核心任务：

1. 从多个可合箱包裹中选择部分包裹，创建一次转运单；
2. 区分“已付款，等待仓库发出”和“已从仓库发出”；
3. 识别当前运输阶段、最近进展和下一预期；
4. 在异常状态下理解发生什么、影响什么、自己需不需要行动。

## 2. Out of Scope

本轮不验证：

- 用户是否有中英集运需求；
- 用户是否喜欢视觉风格；
- 新功能需求、MVP 范围、真实价格或真实物流规则；
- 模拟支付、仓库和物流事件的真实性；
- 正式微信小程序代码或技术实现。

测试中不修改原型、不增加功能、不临时解释设计意图。

## 3. Test Object and Setup

| 项目 | 定义 |
| --- | --- |
| 测试对象 | 本地打开的低保真可点击原型 |
| 使用设备 | 优先手机；也可使用浏览器移动设备模拟模式 |
| 数据 | 原型内置 Mock Data |
| 参与者 | 有中国 → 英国寄送、集运或相近跨境寄送经验的真实用户优先 |
| 建议样本 | 3–5 名探索性可用性测试参与者；结果用于发现交互问题，不用于推断总体比例 |
| 单次时长 | 约 25–35 分钟 |
| 角色 | 1 名主持人；可选 1 名观察记录者 |
| 记录原则 | 使用匿名编号（如 UT01）；不在公开材料中记录姓名、联系方式、订单或地址 |

## 4. Test Questions

| Task | 核心问题 | 不测试什么 |
| --- | --- | --- |
| Task 1：多包裹合箱 | 用户能否找到入口、理解可选状态、选择 8 件并创建转运单？ | 用户是否认为所有人都应该一次寄 8 件 |
| Task 2：判断是否已经出库 | 用户能否仅根据中文状态正确判断“尚未出库”？ | 真实仓库出库时效 |
| Task 3：查看当前物流进度 | 用户能否找到当前阶段、Timeline 和下一预期？ | 承运商事件的真实性或准确性 |
| Task 4：异常处理 | 用户能否理解异常的事实、影响、行动、进展和支持信息？ | 真实异常责任、赔付或客服政策 |

## 5. Test Method

### Moderated Task-based Test

- 每个任务先给出场景和目标，**不**告诉用户应点击的页面、按钮或状态位置。
- 鼓励用户自然操作，并在操作过程中按需说出正在想什么。
- 主持人观察路径、停顿、误解、回退和主动解释，而不纠正用户。
- 每个任务后仅询问回顾实际行为的开放问题，例如：**“刚才哪里最让你犹豫？”**

### Think-aloud Prompt

开始前可说明：

> 操作时如果方便，请说说你正在找什么、为什么准备点这里。没有正确或错误答案，我们测试的是原型，不是测试你。

不应要求用户持续解释，以免影响其自然操作。

## 6. Assistance Policy

| 情况 | 主持人做什么 | 主持人不能做什么 |
| --- | --- | --- |
| 用户短暂停顿 | 保持安静，记录停顿与视线 / 指向 | 立即提示入口 |
| 用户说不知道怎么继续 | 问：**“你现在在找什么？”** | 说“你可以点包裹 / 转运” |
| 用户重复尝试或明显卡住 | 问：**“你期待接下来看到什么？”** | 解释页面设计、状态含义或正确步骤 |
| 用户约 90 秒仍无法继续 | 记录为未完成或需要帮助后，可结束该任务 | 把任务完成路径演示成测试结果 |

若必须提供帮助，记录帮助发生的时间、内容和对任务完成的影响。

## 7. Task Success Definition

成功仅用于记录任务是否完成，不代表产品已被验证或用户需求已被证明。

| Task | Completed | Completed with Help | Not Completed |
| --- | --- | --- | --- |
| Task 1 | 自主选择 8 件可合箱包裹并成功创建转运单 | 在主持人最小帮助后完成 | 未能进入选择、无法理解可选规则或未能提交 |
| Task 2 | 正确回答“还没有从仓库发出” | 获得最小帮助后作出正确判断 | 回答已出库 / 无法判断 |
| Task 3 | 正确说明当前阶段，并指出下一预期阶段 | 获得最小帮助后完成 | 找不到状态或 Timeline，或误解阶段 |
| Task 4 | 找到并能复述发生什么、影响、下一步和进展 / 支持 | 获得最小帮助后完成 | 不能理解异常或不知道下一步 |

## 8. Severity Definition

| Severity | 定义 | 记录原则 |
| --- | --- | --- |
| Critical | 无法完成核心任务。 | 记录卡住位置、已有尝试、是否被迫终止。 |
| Major | 能够完成，但存在明显误解或较大摩擦。 | 记录错误心智模型、回退、额外时间或需帮助。 |
| Minor | 不阻塞任务的小问题。 | 记录文案、层级或操作细节造成的短暂疑惑。 |

严重性描述的是本次任务中的观察，不等同于发生频率或市场影响。

## 9. Test Readiness Checklist

- [ ] 使用原型初始 Mock Data，或按测试脚本指定状态完成重置；
- [ ] 参与者未获得页面操作教学；
- [ ] 主持人与记录者了解 Assistance Policy；
- [ ] 匿名记录表已准备；
- [ ] 如录屏 / 录音，已取得明确同意；
- [ ] 每个任务结束后已重置到下一任务指定起点；
- [ ] 测试结束后不在现场承诺产品修改。
