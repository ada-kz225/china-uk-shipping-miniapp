# 中英集运微信小程序：产品复盘

> 本文是个人作品集中的项目复盘，记录从问题发现到 V1 实现的决策、证据边界与后续方向。它不将单次访谈或单次可用性测试表述为市场结论。

## 1. 问题背景

个人中英集运涉及外部电商下单、中国仓收货与识别、多个包裹的选择与打包、跨境运输、清关和英国末端派送。对用户而言，旅程的困难不只是“寄出一个箱子”，而是在不同阶段判断：哪些包裹已真正可用、这次该寄哪些、付款后是否实际离仓，以及出现问题时下一步是什么。

本项目将产品定位为一个**面向个人中英集运用户的自助信息与决策入口**，而非完整仓储管理、物流调度或客服系统。

## 2. 用户研究与 P01 证据

Discovery 阶段包含一位独立真实用户 P01 的 exploratory interview。P01 是在英国的留学生，描述最近一次转运约有 10–20 个来自多个中国电商渠道的包裹，约每三个月进行一次转运。

| P01 观察 | 对 V1 的有限含义 | 证据边界 |
| --- | --- | --- |
| 国内物流显示送达后，仍会向客服确认仓库是否已收货并归入个人集合 | Package 的“到仓”与“可合箱”需要区分 | 只描述 P01 的服务使用方式，不代表所有仓库规则 |
| 合箱前人工核对多个电商订单是否漏件、错件或未送达，认为过程麻烦 | 需要支持 10–20 件 Package 的盘点、筛选和多选 | 不代表每位用户都以相同数量或频率使用 |
| 会选择部分包裹本次寄出，并在封箱前确认 | Package → Shipment 是核心用户任务，而非一个单一的订单状态 | 不证明所有用户都需要相同合箱规则 |
| 付款后仍需询问是否已经离仓；时差下客服回复有时需等待 | 付款与实际出库必须区分，并提供连续状态 | 不构成真实服务时效承诺 |
| 英国末端派送曾长时间停滞，最终通过电话联系承运商 | 异常需要解释影响与下一步 | 异常频率、具体原因和支持策略仍未知 |

P01 支持了当前设计方向，但只有一个独立样本。因此多包裹行为、微信小程序入口适配性、预报规则、报价规则和外部数据可用性继续被标为 Product Assumption。详见 [Discovery 结论](../01-research/12-discovery-conclusion.md)。

## 3. 为什么选择当前 MVP

V1 没有从“功能清单”开始，而是围绕三个核心 JTBD 收敛：

1. 当多个国内包裹陆续到仓时，确认它们是否到仓并归属自己，从而判断能否合箱；
2. 当有一批可处理包裹时，选择本次寄出的包裹并提交转运单；
3. 当转运单已称重、报价和付款后，自助确认是否离仓及后续履约。

因此，V1 的边界是 Package 管理、Shipment 创建、报价/模拟付款、出库后的最小履约追踪与异常指引。优惠、会员、完整客服、完整 WMS、多国线路、真实支付和真实物流接入均没有进入 P0。

## 4. 关键产品决策

### Package 与 Shipment 分离

Package 表示一件待识别、待确认或可被选择的实物包裹；Shipment 表示一次由多个 Package 组成的寄送履约。该拆分让“哪些东西到了”和“这次要寄什么”成为两个清晰的用户任务。

```text
多个 Package（到仓 / 匹配 / 可合箱）
              ↓ 用户选择并提交
一个 Shipment（处理 / 报价 / 付款 / 出库 / 履约）
```

服务端在提交 Shipment 时原子校验并锁定 Package，避免同一 Package 同时进入两张有效转运单。

### 已付款不等于已出库

P01 会在付款后继续确认是否离仓。因此 `PAID_AWAITING_DISPATCH`、`DISPATCHED` 和 `DELIVERED` 被建模为三个不同事实。用户界面统一使用中文文案，例如“已付款，等待仓库发出”，不展示内部英文状态码。

### 状态必须有下一步

转运单详情始终同时表达当前状态、含义与下一步。异常不只是红色标签，而是回答五个问题：发生什么、影响什么、用户需要做什么、当前处理进度、如何获得帮助。

### 首页不是功能入口九宫格

首页按用户优先级聚合：待处理事项 → 当前运输 → 包裹概览 → 中国仓库信息。异常和待付款优先于普通状态；“已付款待出库”仅表示进度，不被误导为待办。

## 5. 10–20 件 Package 如何影响多选设计

P01 的 10–20 件包裹场景改变了多选流程的设计重点：

- 只让 `READY_FOR_SHIPMENT` 状态的包裹可选；
- 对不可选包裹直接展示中文原因，而非让用户点击后才报错；
- 选择模式显示已选数量与仍未选择的可合箱数量，但不强制用户全部选择；
- 提交前清楚展示已选 Package、可移除操作和英国地址；
- 提交时由后端重新校验可用性，并原子锁定，避免前端看到的状态与实际数据脱节。

这不是对所有用户行为的断言，而是针对当前 MVP 主要场景的设计选择。

## 6. Prototype Usability Test

UT01 是一次真实 exploratory usability test，覆盖多 Package 合箱、判断是否出库、查询物流、异常处理四项任务。参与者在无提示下完成四项任务，但发现两项真实问题：

| 问题 | 严重性 | 修改 | 回归结果 |
| --- | --- | --- | --- |
| 连续选择包裹时页面自动回到顶部 | Major | 保留当前滚动位置 | UT01 连续选择 8 件时未再回顶 |
| 创建转运单时“移除”位置不稳定 | Minor | 将移除操作固定在每行右侧 | UT01 无提示找到右侧操作 |

该结果只支持 UT01 的测试场景，不能外推为普遍可用性结论。详情见 [Usability Findings](../06-usability-testing/05-usability-findings.md)。

## 7. 开发中的问题与迭代

实现阶段继续把产品规则落实为可测试的状态约束，并在人工验收后完成以下质量修正：

| 发现 | 处理方式 | 为什么重要 |
| --- | --- | --- |
| 微信端无请求正文的操作会以空 `application/json` 到达服务端 | 服务端将空 JSON 正文解析为无正文，并保留非空无效 JSON 的结构化 400 错误 | 草稿移除与取消不应因为传输格式而变成“服务器不可用” |
| 多选场景中不可选包裹视觉不够明确 | 不可选卡片灰化、禁用选择并显示中文原因 | 用户应在选择前知道哪些包裹不能加入本次转运 |
| 长列表的筛选与底部操作需要同时可见 | 筛选条支持横向访问并显示真实数量；底部操作区为稳定位置并预留内容空间 | 支持 10–20 件包裹的连续判断与操作 |
| 用户可能把付款完成理解为已经发货 | 后端设置 Dispatch 闸门，界面明确“已付款，等待仓库发出” | 防止支付事实与物理出库事实混淆 |

这些改动不扩展 MVP Scope，均服务于已冻结的核心任务流。

## 8. 用户端、Backend Ops 与模拟外部系统的拆分

| 层级 | V1 承担的职责 |
| --- | --- |
| 用户端微信小程序 | 查询状态、预报包裹、选择包裹、提交转运单、查看报价、模拟付款、理解履约与异常下一步 |
| Backend / Ops | 用户归属、状态机、Package 锁定、报价快照、付款与出库闸门、运输事件顺序、异常阻断/恢复、审计记录 |
| 模拟外部系统 | 仓库收货/匹配/称重/出库、付款结果、国内与国际物流、清关、英国派送与签收事件 |

这种拆分避免把“界面显示一个状态”误认为“系统已经拥有真实业务集成”。用户端看到的状态由后端规则产生；外部事实来源在作品集 V1 中明确为模拟。

## 9. 当前限制

- 只有一位独立真实访谈参与者 P01；研究结论不能外推为广泛用户结论；
- UT01 同样只有一位用户，属于探索性可用性证据；
- 微信小程序作为商业入口仍是 Product Assumption；
- 没有真实微信登录、微信支付、仓库、承运商、海关或末端派送集成；
- 演示数据、报价、运输时间和异常场景均为虚构，用于验证交互和状态逻辑；
- 尚未进行真机、多网络条件或更大包裹规模的系统化回归。

## 10. Future Iterations

1. 扩展真实用户研究，并验证核心人群、包裹规模、预报规则和入口偏好；
2. 在更多用户与设备上复测 10–20 件包裹的选择、异常理解和付款后离仓认知；
3. 优先验证照片凭据、状态通知、地址簿和有限增值服务是否值得进入下一版；
4. 在明确业务合作与合规前提后，再评估真实认证、支付、仓库作业和物流数据接入；
5. 为外部集成补充可观测性、权限、安全、失败重试和支持策略。
